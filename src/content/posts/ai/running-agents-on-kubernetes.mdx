<AnswerBlock question="Agent API와 Worker는 Kubernetes에서 어떻게 배포해야 하는가?">
  <strong>Worker는 Kubernetes의 특별한 resource가 아니라 queue에서 실행 시도를 맡는 애플리케이션 역할이다.</strong> API와 Worker는 같은 image를 사용할 수 있지만 서로 다른 Deployment로 운영하는 편이 자연스럽다. API는 HTTP 요청과 연결에 맞춰, Worker는 queue backlog·작업 시간·하위 서비스 한도에 맞춰 확장한다. Worker 종료 시에는 새 job 수신을 멈추고 진행 중인 작업을 마무리하거나 복구 가능하게 남긴 뒤 종료해야 한다.
</AnswerBlock>

[Worker는 Thread가 아니다](/ai/agents/worker-is-not-thread/)에서는 Worker를 실행 lifecycle의 ownership boundary로 정의했다. [Worker가 죽으면 어떻게 되는가](/ai/agents/when-workers-die/)에서는 ack되지 않은 Redis Stream entry가 PEL에 남고 다른 consumer가 회수하는 흐름을 만들었다.

이제 그 Worker를 Kubernetes에 올려보자. 여기서 흔한 오해는 “Worker Pod”라는 별도 종류의 Kubernetes 객체가 있다고 생각하는 것이다. Kubernetes가 아는 것은 `Pod`, `Deployment`, `Job` 같은 workload resource다. **Worker라는 의미는 container 안에서 실행되는 애플리케이션이 부여한다.**

```text
같은 image: my-agent:1.0

API Deployment                 Worker Deployment
└─ uvicorn app.api:app         └─ python -m app.worker
   HTTP lifecycle                 queue/job lifecycle
```

같은 repository와 image를 공유하면서 command, replica 수, 자원, 비밀정보, 배포 속도와 확장 기준을 다르게 둘 수 있다.

## 분리 기준은 코드가 아니라 수명주기다

API와 Worker의 차이는 directory 구조보다 운영 특성에서 드러난다.

| 구분 | API Deployment | Worker Deployment |
| --- | --- | --- |
| 주된 입력 | HTTP request, SSE connection | Queue entry |
| 일반적인 작업 시간 | 짧고 예측 가능 | 수초에서 수분, 편차 큼 |
| 확장 신호 | request rate, latency, connection 수 | queue lag, pending, oldest age |
| 종료 시 핵심 | 새 traffic 제거, 진행 중 request drain | 새 job 수신 중단, in-flight attempt 정리 |
| 주요 병목 | socket, DB pool, 인증 | LLM/tool quota, 메모리, CPU/GPU |
| 필요한 비밀정보 | 사용자 인증, 조회용 credential | tool 실행용 credential |

처음에는 한 process에서 함께 실행할 수 있다. 하지만 배포 한 번으로 API 연결과 장시간 run이 동시에 끊기고, 같은 replica 수와 자원 profile을 강요받는다면 이미 서로 다른 lifecycle을 한 단위에 묶은 비용이 나타난 것이다.

```python
# One image, two entry points.
def api_main() -> None:
    uvicorn.run("app.api:app", host="0.0.0.0", port=8000)

def worker_main() -> None:
    asyncio.run(run_worker())
```

## 두 Deployment는 같은 image를 사용할 수 있다

API Deployment의 최소 형태는 다음과 같다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: agent-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: agent-api
  template:
    metadata:
      labels:
        app: agent-api
    spec:
      containers:
        - name: api
          image: registry.example.com/my-agent:1.0
          command: ["uvicorn", "app.api:app"]
          args: ["--host", "0.0.0.0", "--port", "8000"]
          ports:
            - containerPort: 8000
```

Worker는 Service로 외부에 공개할 필요 없이 같은 image에서 다른 command를 실행할 수 있다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: agent-worker
spec:
  replicas: 2
  selector:
    matchLabels:
      app: agent-worker
  template:
    metadata:
      labels:
        app: agent-worker
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: worker
          image: registry.example.com/my-agent:1.0
          command: ["python", "-m", "app.worker"]
```

예시의 replica와 120초는 권장 기본값이 아니다. 실제 queue wait SLO, run 시간 분포, reclaim timeout, downstream quota를 측정해 정해야 한다.

## 일반 Agent run마다 Kubernetes Job을 만들 필요는 없다

Kubernetes `Job`은 완료될 때까지 하나 이상의 Pod를 실행하는 workload controller다. 이름이 job이라고 해서 애플리케이션의 모든 `run_id`를 Kubernetes Job 하나와 대응해야 하는 것은 아니다.

```text
Request마다 Kubernetes Job
request → API object 생성 → scheduling → image start → execute → cleanup

Long-lived Worker Deployment
request → queue → 이미 실행 중인 worker가 즉시 consume
```

짧은 run이 자주 들어오는 서비스라면 장시간 살아 있는 Worker Deployment가 scheduling과 container startup 비용을 amortize한다. 반대로 몇 시간짜리 batch, 강한 자원 격리, run별 다른 GPU·image·권한이 필요하면 Kubernetes Job이 더 자연스러울 수 있다.

선택 기준은 “비동기 작업인가?”가 아니라 다음에 가깝다.

- 작업 빈도와 startup overhead의 비중
- run별 자원과 보안 격리 필요성
- worker process 안에서 안전하게 공유할 connection/model cache
- Kubernetes object 수와 cleanup 부담
- queue가 이미 제공하는 재시도와 Kubernetes Job 재시도의 중복

두 retry layer를 동시에 켜면 한 실패가 queue 재전달과 Job 재시작으로 곱해질 수 있다. 어느 layer가 attempt를 소유하는지 명확히 해야 한다.

## Worker process 안에서도 동시성에 상한을 둔다

Pod 두 개라는 정보만으로 실제 in-flight run 수를 알 수 없다. I/O 중심 Worker는 process 하나에서 여러 coroutine을 실행할 수 있다.

```text
2 Pods × Pod당 4 in-flight runs = 최대 8 concurrent runs
```

```python
class Worker:
    def __init__(self, max_in_flight: int = 4):
        self.accepting = True
        self.limit = asyncio.Semaphore(max_in_flight)
        self.tasks: set[asyncio.Task] = set()

    async def dispatch(self, message) -> None:
        await self.limit.acquire()
        task = asyncio.create_task(self.handle(message))
        self.tasks.add(task)
        task.add_done_callback(self.tasks.discard)
        task.add_done_callback(lambda _: self.limit.release())
```

상한은 CPU만 보고 정하지 않는다. PostgreSQL pool, Redis connection, LLM rate limit, tool API quota, run당 peak memory를 함께 본다. Replica autoscaling과 process 내부 concurrency는 같은 용량을 조절하는 두 개의 손잡이다.

```text
총 잠재 동시 실행
≈ worker replicas × process당 max_in_flight
```

Replica만 늘리면서 LLM provider quota를 그대로 두면 throughput은 늘지 않고 429와 retry만 증가할 수 있다.

## SIGTERM은 Worker에게 drain을 시작하라는 신호다

Deployment rollout이나 scale-down이 시작되면 Pod는 종료 절차에 들어간다. Kubernetes는 설정된 grace period 안에서 container process에 종료 신호를 보내고, 시간이 끝난 뒤에도 남은 process는 강제 종료될 수 있다. 애플리케이션은 이 시간을 의식해야 한다.

Worker의 종료 protocol은 다음과 같다.

```text
SIGTERM
  ↓
새 XREADGROUP 중단
  ↓
in-flight task에 종료 의도 전달
  ↓
완료 가능한 작업은 결과 저장 후 XACK
  ↓
끝내지 못한 작업은 ack하지 않고 복구 가능하게 남김
  ↓
process exit
```

```python
import asyncio
import signal

stop = asyncio.Event()

def request_shutdown() -> None:
    stop.set()

async def worker_main() -> None:
    loop = asyncio.get_running_loop()
    loop.add_signal_handler(signal.SIGTERM, request_shutdown)
    loop.add_signal_handler(signal.SIGINT, request_shutdown)

    worker = Worker(max_in_flight=4)
    await worker.consume_until(stop)
    await worker.drain(timeout=100)
```

`drain()` timeout은 `terminationGracePeriodSeconds`보다 짧아야 정리와 process exit 시간을 남길 수 있다. 제한 시간 안에 완료하지 못한 job은 억지로 `XACK`하지 않는다. 앞선 글의 reclaim path가 이어받도록 PEL에 남긴다.

`preStop` hook을 쓸 수도 있지만 hook 실행 시간도 Pod의 termination grace period에 포함된다. 단순 `sleep`만 추가하면 종료가 안전해지는 것은 아니다. Queue 수신 중단과 attempt state 전환은 애플리케이션이 명시적으로 구현해야 한다.

## Probe는 서로 다른 질문에 답한다

API Pod와 Worker Pod에 같은 probe를 복사하면 의미가 흐려진다.

| Probe | 질문 | 실패 시 효과 |
| --- | --- | --- |
| startup | 애플리케이션이 시작을 끝냈는가? | 성공 전 liveness/readiness 지연 |
| readiness | 지금 traffic을 받을 준비가 됐는가? | Service endpoint에서 제외 |
| liveness | process를 재시작해야만 회복되는가? | container restart |

API readiness는 새 HTTP 요청을 받을 수 있는지 확인한다. Worker는 외부 Service traffic을 받지 않으므로 readiness를 queue consumption gate로 자동 연결해주지 않는다. Worker 자신이 dependency state와 drain flag를 보고 수신 여부를 결정해야 한다.

```python
@app.get("/ready")
async def ready():
    if draining.is_set():
        raise HTTPException(503, "draining")
    if not await critical_dependencies_available():
        raise HTTPException(503, "dependency unavailable")
    return {"ready": True}
```

Liveness probe가 외부 LLM이나 일시적인 database 장애까지 확인하게 만들면 전체 Worker가 동시에 재시작해 장애를 키울 수 있다. Liveness는 deadlock처럼 **restart가 실제 회복 방법인 state**에 좁게 사용한다.

## Requests와 limits는 측정값에서 시작한다

Kubernetes scheduler는 resource request를 사용해 Pod를 배치하고, runtime은 limit을 집행한다. CPU limit에 도달하면 throttling이 발생할 수 있고 memory limit을 넘으면 process가 OOM 종료될 수 있다.

```yaml
containers:
  - name: worker
    resources:
      requests:
        cpu: "500m"
        memory: "1Gi"
      limits:
        cpu: "2"
        memory: "3Gi"
```

이 숫자도 illustrative example이다. 다음 분포를 계측한 뒤 조정한다.

- idle과 active의 CPU·memory working set
- run 하나가 추가될 때의 peak memory
- parsing, reranking, local inference의 CPU burst
- OOM과 restart 횟수
- CPU throttling과 run latency의 상관관계

API와 Worker는 서로 다른 profile을 갖는다. API는 낮은 latency와 connection 안정성이 중요하고, Worker는 작업별 memory peak가 크며 일부 CPU-heavy node가 event loop를 오래 점유할 수 있다.

CPU-heavy parser나 model inference가 충분히 크다면 별도 workload로 분리한다.

```text
agent-worker Deployment
└─ I/O-heavy orchestration, bounded async concurrency

cpu-worker Deployment
└─ parsing/reranking, lower concurrency, larger CPU request

inference Deployment
└─ GPU, batching, model-serving lifecycle
```

## API와 Worker는 서로 다른 신호로 확장한다

API는 CPU, request rate, latency 또는 active connection을 기준으로 확장할 수 있다. Worker는 CPU가 낮아도 queue가 쌓일 수 있다. 대부분의 시간이 외부 LLM 응답 대기라면 CPU 기반 HPA만으로 수요를 보지 못한다.

Worker가 봐야 할 신호는 다음과 같다.

```text
undelivered queue lag
+ reclaim 가능한 pending work
+ oldest job age
+ observed service time
```

목표를 단순화하면 다음처럼 생각할 수 있다.

```python
import math

def desired_replicas(outstanding: int, target_per_pod: int) -> int:
    return max(1, math.ceil(outstanding / target_per_pod))
```

하지만 실제 상한은 downstream capacity가 정한다.

```text
desired replicas
≤ DB connection budget / connections per Pod
≤ LLM request budget / requests per Pod
≤ tool API quota / calls per Pod
```

Kubernetes HPA는 custom/external metric을 사용할 수 있고, KEDA는 Redis Streams를 포함한 event source를 위한 scaler를 제공한다. 다만 scaler가 어떤 값을 lag 또는 pending으로 계산하는지, scale-to-zero에서 첫 consumer가 어떻게 시작되는지, 인증정보를 어떻게 제공하는지는 사용 중인 KEDA 버전 문서로 검증해야 한다.

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: agent-worker
spec:
  scaleTargetRef:
    name: agent-worker
  minReplicaCount: 1
  maxReplicaCount: 20
  triggers:
    - type: redis-streams
      metadata:
        address: redis.example:6379
        stream: agent:jobs
        consumerGroup: agent-workers
        lagCount: "5"
```

이 manifest는 개념 예시다. production에서는 `TriggerAuthentication` 또는 workload identity 등으로 credential을 분리하고 TLS, Redis topology, cooldown과 polling interval을 함께 설정한다.

## 배포는 보안 경계도 더 선명하게 만든다

API와 Worker가 같은 image를 사용해도 같은 권한을 가질 필요는 없다.

- API ServiceAccount는 session/run 접수와 조회에 필요한 권한만 가진다.
- Worker ServiceAccount는 실행에 필요한 tool과 result storage에 접근한다.
- 사용자 identity는 queue payload의 임의 field가 아니라 검증된 run record에서 읽는다.
- NetworkPolicy로 Worker의 ingress를 막고 필요한 egress를 제한한다.
- secret은 image나 environment dump에 포함하지 않고 namespace와 workload 범위로 관리한다.

Worker가 더 강한 tool credential을 가진다면 API의 SSRF나 임의 tool 호출 취약점이 Worker까지 직통으로 이어지지 않게 command schema와 queue producer 권한을 제한해야 한다.

## Rollout과 scale-down을 장애 테스트로 다룬다

Kubernetes manifest가 적용된다고 안전한 배포가 증명되는 것은 아니다.

| Test | 확인할 invariant |
| --- | --- |
| 실행 중 `kubectl rollout restart` | 새 job은 다른 Pod가 받고 기존 job은 완료 또는 pending 복구 |
| Worker replica를 0 또는 1로 축소 | drain 뒤 미완료 entry를 ack하지 않음 |
| grace period보다 긴 tool call | SIGKILL 뒤 다른 worker가 reclaim |
| memory limit을 의도적으로 초과 | OOM 뒤 run이 영구 `running`에 머물지 않음 |
| Redis 일시 장애 | liveness 재시작 폭주 없이 backoff |
| LLM 429 증가 | replica 증가가 retry storm을 만들지 않음 |
| API rollout 중 SSE 연결 | 재연결 cursor로 event 복원 |

```python
async def test_worker_rollout_preserves_job(k8s, run_store):
    run_id = await submit_long_run()
    old_pod = await wait_until_running(run_id)

    await k8s.delete_pod(old_pod)

    result = await wait_for_terminal(run_id, timeout=300)
    assert result.status == "succeeded"
    assert await run_store.active_attempt_count(run_id) <= 1
```

이 테스트에서 중요한 것은 동일 Pod가 살아남는지가 아니다. Pod는 교체 가능하다. **Run의 durable identity와 복구 규칙이 살아남는지**가 중요하다.

## 구현 체크리스트

- Worker를 Kubernetes resource type이 아니라 애플리케이션 역할로 정의했는가?
- API와 Worker의 lifecycle, resource profile, credential과 확장 신호가 다른가?
- 같은 image를 쓰더라도 별도 Deployment와 command로 실행하는가?
- Kubernetes Job을 선택한다면 per-run isolation의 이점이 startup 비용보다 큰가?
- Pod당 in-flight run 수에 명시적인 상한이 있는가?
- SIGTERM 이후 새 queue entry 수신을 중단하는가?
- grace period 안에 끝내지 못한 job을 ack하지 않는가?
- startup, readiness, liveness probe의 의미를 구분하는가?
- requests/limits를 실제 workload 분포로 조정하는가?
- Worker scaling이 CPU뿐 아니라 queue lag와 oldest age를 보는가?
- replica 증가가 DB·LLM·tool quota를 넘지 않도록 상한을 두는가?
- rollout, scale-down, OOM, SIGKILL을 포함한 통합 테스트가 있는가?

## 이제 하나의 요청을 처음부터 끝까지 연결할 수 있다

지금까지 API/Worker 경계, PostgreSQL과 Redis state, snapshot과 event, SSE, LangGraph runtime, session/run isolation, queue recovery와 Kubernetes deployment를 각각 분리해 살펴봤다. 각각의 구성 요소는 특정 실패를 해결하지만, 실제 사용자의 요청은 이 모든 경계를 한 번에 통과한다.

다음 글에서는 `POST /sessions/{session_id}/runs`에서 시작해 durable run 생성, queue publish, Worker claim, LangGraph 실행, state/event 갱신, 결과 저장, `XACK`, SSE 재연결까지 하나의 request를 끝까지 추적한다. 구성 요소 목록이 아니라 **어느 시점에 누가 무엇을 소유하는가**를 하나의 sequence로 합친다.
