앞선 글 [Agent는 얼마나 오래 생각해야 하는가](/ai/agents/timeouts-deadlines-and-budgets/)에서는 하나의 run에 deadline과 token·cost·retry budget을 부여했다. 마지막에는 질문 하나가 남았다.

> 승인을 기다리는 동안에도 deadline이 계속 흐르는가? 몇 시간 뒤 승인되면 어디서 다시 시작하는가?

가장 단순한 Human-in-the-Loop 구현은 Worker 안에서 기다린다.

```python
async def send_report(state):
    approved = await wait_for_human_approval(state["draft"])
    if approved:
        return await email_tool.send(state["draft"])
```

이 방식은 승인 시간 동안 Worker slot, DB connection, Queue delivery와 memory를 붙잡는다. Pod가 교체되면 기다리던 coroutine도 사라진다. 다시 실행하면 draft 생성부터 반복하고, 이미 발생한 side effect까지 재실행할 수 있다.

Durable HITL의 pause는 sleeping coroutine이 아니다. **실행 ownership을 반납해도 다시 찾을 수 있는 durable state**다.

## Checkpoint는 중요한 기록이지만 모든 진실은 아니다

LangGraph checkpointer는 thread의 graph state를 checkpoint로 저장한다. Conversation continuity, failure recovery와 interrupt 재개에 적합하다. 반면 store는 thread 바깥의 application-defined data에 사용된다.

Production Agent backend에는 적어도 네 기록이 있다.

| 기록 | 책임 | 대표 필드 |
| --- | --- | --- |
| Graph checkpoint | runtime state와 다음 실행 위치 | `thread_id`, `checkpoint_id`, state, pending task |
| Run record | 사용자에게 보이는 lifecycle | `run_id`, status, result, active attempt |
| Approval record | 권한·감사·만료가 있는 결정 | `approval_id`, action digest, decision, reviewer |
| Execution ledger | 이미 발생한 외부 실행 | `tool_call_id`, idempotency key, remote result |

Graph checkpoint가 존재한다고 run이 승인된 것은 아니다. Approval row가 `approved`여도 어떤 action을 승인했는지 일치하지 않으면 실행할 수 없다. Graph state에 `email_sent=True`가 있어도 외부 provider와 application ledger가 다르면 복구 판단이 필요하다.

Checkpoint는 framework state다. Product lifecycle과 authorization을 checkpointer 내부 구조에만 숨기지 않는다.

## ID마다 가리키는 대상이 다르다

Resume bug는 ID를 하나로 합칠 때 자주 생긴다.

| ID | 질문 |
| --- | --- |
| `session_id` | 어떤 지속 대화 context인가? |
| `run_id` | 어떤 사용자 실행인가? |
| `attempt_id` | 어떤 Worker 시도가 실행 권한을 가졌나? |
| `thread_id` | Checkpointer가 어떤 runtime history를 읽나? |
| `checkpoint_id` | 그 history의 어느 snapshot인가? |
| `interrupt_id` | 어떤 pause 지점의 입력을 기다리나? |
| `approval_id` | 어떤 제품 승인 요청인가? |
| `tool_call_id` | 어떤 외부 action의 실행 이력인가? |

앞선 글들처럼 한 session에 active run 하나만 허용한다면 `thread_id=session_id`를 사용할 수 있다. 대신 checkpoint metadata에 `run_id`를 남기고, resume할 때 현재 active run과 일치하는지 검증한다.

```python
config = {
    "configurable": {
        "thread_id": str(run.session_id),
    },
    "metadata": {
        "run_id": str(run.id),
        "attempt_id": str(attempt.id),
        "graph_version": GRAPH_VERSION,
    },
}
```

같은 session에서 run을 병렬로 허용한다면 run-scoped `thread_id`나 checkpoint namespace가 더 안전하다. 중요한 것은 어떤 mapping을 택하든 DB에 명시하고 resume request가 추측하지 않게 하는 것이다.

## Pause는 상태 전이이자 ownership handoff다

실행은 `interrupt()`에 도달했다고 바로 안전하게 pause된 것이 아니다. Checkpoint와 product approval을 다시 찾을 수 있고, 현재 Queue delivery를 정리할 수 있어야 한다.

권장 lifecycle은 다음과 같다.

```text
running
  → pausing
  → waiting_approval
  → resume_queued
  → resuming
  → running
  → succeeded | failed | cancelled

waiting_approval
  → rejected | expired | cancelled
```

`waiting_approval`은 “Worker가 기다리는 중”이 아니다. Graph checkpoint와 pending approval이 durable하고, 어떤 Worker도 active attempt를 소유하지 않는 상태다.

## Approval action을 먼저 고정한다

“이메일 발송을 승인합니까?”만 저장하면 resume 시 다른 recipient나 body로 바뀌는 TOCTOU 문제가 생긴다. 승인 대상 payload를 canonicalize하고 digest를 만든다.

```python
import hashlib
import json

def action_digest(action: dict) -> str:
    canonical = json.dumps(
        action,
        sort_keys=True,
        separators=(",", ":"),
        ensure_ascii=False,
    )
    return hashlib.sha256(canonical.encode()).hexdigest()
```

Approval record에는 사람이 판단할 snapshot과 기계가 검증할 digest를 함께 저장한다.

```sql
INSERT INTO approvals (
    approval_id,
    tenant_id,
    run_id,
    interrupt_id,
    checkpoint_id,
    action_type,
    action_payload_json,
    action_digest,
    status,
    expires_at
)
VALUES ($1, $2, $3, $4, $5, $6, $7, $8, 'pending', $9)
ON CONFLICT (approval_id) DO NOTHING;
```

`approval_id`는 `run_id + logical_action_id + action_version`처럼 stable하게 만든다. Worker가 checkpoint 저장 직후 죽어 같은 interrupt에 다시 도달해도 pending request가 중복 생성되지 않는다.

내용을 편집하면 기존 승인에 다른 payload를 끼워 넣지 않는다. `action_version`을 올리고 새 digest와 새 승인 요청을 만든다.

## LangGraph interrupt는 pause point를 만든다

Graph는 production durable checkpointer와 안정적인 `thread_id`로 compile한다.

```python
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from langgraph.types import interrupt

async with AsyncPostgresSaver.from_conn_string(DB_URI) as checkpointer:
    await checkpointer.setup()
    graph = builder.compile(checkpointer=checkpointer)

def approval_node(state: AgentState):
    decision = interrupt({
        "approval_id": state["approval_id"],
        "action": state["pending_action"],
        "action_digest": state["action_digest"],
        "expires_at": state["approval_expires_at"],
    })
    return {"approval_decision": decision}
```

`InMemorySaver`는 process restart 뒤 checkpoint가 사라지므로 production durability를 제공하지 않는다. Interrupt payload도 JSON-serializable data로 유지한다. Credential이나 거대한 document를 복제하지 않고 reference와 review snapshot만 전달한다.

Graph가 interrupt를 반환하면 Worker는 이를 application contract로 투영한다.

```python
result = await graph.ainvoke(input_state, config=config)

if interrupts := result.get("__interrupt__"):
    pending = interrupts[0]
    await pause_run(
        run=run,
        attempt=attempt,
        interrupt=pending,
    )
```

정확한 API projection은 LangGraph 버전에 따라 달라질 수 있지만 architecture 경계는 같다. Runtime interrupt를 그대로 UI authorization으로 쓰지 않고 durable approval entity로 변환한다.

## Pause가 durable해진 뒤 현재 Queue entry를 ack한다

몇 시간 동안 Redis Stream PEL에 entry를 남겨 두는 것은 승인 대기가 아니라 미확인 delivery다. Reclaimer가 가져가 graph를 다시 실행할 수 있고 pending 수치도 왜곡된다.

<AgentResumeDiagrams
  kind="handoff"
  language="ko"
  caption="그림 3. Interrupt 뒤 현재 delivery를 종료하고, 승인 결정이 별도의 resume delivery를 만든다."

Pause protocol의 순서는 다음과 같다.

```text
1. Checkpointer가 interrupt state를 durable하게 저장
2. Product DB에 approval pending + run waiting_approval 기록
3. approval_requested event append
4. 현재 Queue entry XACK
5. Worker attempt release
```

```python
async with db.transaction():
    approval = await approval_store.upsert_pending(
        run=run,
        interrupt=interrupt,
        action_digest=interrupt.value["action_digest"],
    )
    await run_store.mark_waiting_approval(
        run_id=run.id,
        attempt_id=attempt.id,
        fence=attempt.fence,
        approval_id=approval.id,
        checkpoint_id=approval.checkpoint_id,
    )
    await outbox.append("approval_requested", approval.to_event())

await queue.ack(entry_id)
```

Product DB write가 실패하면 `XACK`하지 않는다. Redelivery된 Worker는 같은 stable approval ID로 upsert하고 pause protocol을 완성한다.

## 승인 API는 graph를 직접 실행하지 않는다

Reviewer 요청의 첫 책임은 authorization과 atomic decision이다.

```python
@app.post("/runs/{run_id}/approvals/{approval_id}/decision")
async def decide_approval(
    run_id: UUID,
    approval_id: UUID,
    request: ApprovalDecision,
    identity: Annotated[Identity, Depends(current_identity)],
):
    return await approval_service.decide(
        tenant_id=identity.tenant_id,
        reviewer=identity,
        run_id=run_id,
        approval_id=approval_id,
        decision=request,
    )
```

Transaction 안에서 pending row를 lock하고 다음을 확인한다.

- Reviewer에게 이 action type과 금액을 승인할 권한이 있는가?
- Approval이 아직 `pending`이며 만료되지 않았는가?
- Run이 여전히 `waiting_approval`이고 같은 approval을 기다리는가?
- Client가 본 `action_digest`와 저장된 digest가 같은가?
- Cancel이나 다른 decision이 먼저 commit되지 않았는가?

```sql
SELECT *
FROM approvals
WHERE approval_id = $1
  AND tenant_id = $2
FOR UPDATE;
```

검증 후 decision과 resume outbox를 같은 transaction에 쓴다.

```python
async with db.transaction():
    approval = await approval_store.lock(approval_id, tenant_id)
    validate_decision(approval, run, reviewer, request)

    await approval_store.commit_decision(
        approval_id=approval.id,
        decision=request.decision,
        reviewer_id=reviewer.user_id,
        note=request.note,
    )
    await run_store.mark_resume_queued(run.id, approval.id)
    await outbox.append(
        "run_resume_requested",
        {"run_id": str(run.id), "approval_id": str(approval.id)},
    )
```

API request가 끊겨도 decision은 durable하다. Outbox relay가 resume job을 Queue에 게시한다. 같은 결정이 반복되면 기존 decision을 반환하고 새 resume를 중복 생성하지 않는다.

## Resume은 새 Worker attempt다

승인한 API process가 graph를 계속 실행하지 않는다. Resume job을 받은 Worker가 새 `attempt_id`와 fencing token을 얻는다.

```python
run = await run_store.get_for_resume(run_id)
approval = await approval_store.get(approval_id)

assert run.status == "resume_queued"
assert run.pending_approval_id == approval.id
assert approval.action_digest == run.pending_action_digest

attempt = await run_store.start_resume_attempt(
    run_id=run.id,
    checkpoint_id=approval.checkpoint_id,
)
```

그 뒤 같은 `thread_id`와 승인 payload로 graph를 재개한다.

```python
from langgraph.types import Command

config = {
    "configurable": {"thread_id": run.thread_id},
    "metadata": {
        "run_id": str(run.id),
        "attempt_id": str(attempt.id),
        "fence": attempt.fence,
    },
}

result = await graph.ainvoke(
    Command(resume={
        "approval_id": str(approval.id),
        "decision": approval.decision,
        "action_digest": approval.action_digest,
    }),
    config=config,
)
```

Resume Worker는 graph를 부르기 전 plan version, graph version과 state schema version도 확인한다. 오래된 checkpoint가 새 deployment와 호환되지 않으면 조용히 실행하지 말고 migration, 이전 runtime routing 또는 명시적 incompatibility 처리 중 하나를 선택한다.

## Resume은 source code의 다음 줄에서 시작하지 않는다

LangGraph interrupt가 있는 node는 resume 시 node 시작부터 다시 실행된다. `interrupt()` 이전 코드도 반복된다.

<AgentResumeDiagrams
  kind="replay"
  language="ko"
  caption="그림 4. Node replay를 전제로 interrupt 이전 코드를 멱등하게 만들고 side effect를 별도 node로 격리한다."

다음 코드는 위험하다.

```python
def approval_node(state):
    audit_id = audit_store.insert("approval_started")
    email_tool.send("approval requested")

    approved = interrupt({"action": state["pending_action"]})
    return {"approved": approved, "audit_id": audit_id}
```

Resume 때 audit row와 email이 다시 생성될 수 있다. 가장 단순한 해법은 approval node가 pause만 담당하고 side effect를 다른 node로 옮기는 것이다.

```python
def approval_node(state):
    decision = interrupt({
        "approval_id": state["approval_id"],
        "action": state["pending_action"],
    })
    return {"approval_decision": decision}

async def execute_effect_node(state):
    if state["approval_decision"]["decision"] != "approved":
        return {"effect_status": "skipped"}

    result = await execution_ledger.execute_once(
        key=f'{state["run_id"]}:{state["logical_action_id"]}',
        action=lambda: email_tool.send(state["pending_action"]),
    )
    return {"effect_status": result.status}
```

Checkpoint는 “이 node를 지나갔다”를 복원하고, execution ledger는 “외부 action이 실제로 실행됐는가”를 증명한다. Worker가 side effect 성공 후 다음 checkpoint 전에 죽는 failure window 때문에 둘 다 필요하다.

## 승인 대기 시간과 deadline을 구분한다

이전 글의 `deadline_at`을 승인 대기 중 무조건 연장하면 사용자가 요청한 latency contract가 사라진다. 반대로 몇 시간짜리 업무 승인을 120초 interactive deadline에 넣으면 durable HITL이 불가능하다.

정책을 두 시간축으로 분리할 수 있다.

| 시간축 | 의미 | Pause 중 동작 |
| --- | --- | --- |
| Execution budget | Worker가 실제 계산에 쓸 수 있는 시간 | 보존하거나 별도 정책으로 차감 |
| Business expiry | 이 action과 승인이 언제까지 유효한가 | 계속 흐름 |

```python
if approval.expires_at <= now:
    await expire_approval(approval.id)
    await run_store.mark_expired(run.id, reason="approval_expired")
    return

if run.remaining_execution_seconds <= MIN_RESUME_BUDGET:
    await run_store.mark_expired(run.id, reason="execution_budget_exhausted")
    return
```

Interactive run은 pause 중에도 원래 run deadline을 유지할 수 있다. 장시간 workflow는 pause 시 active execution timer를 멈추되 immutable `expires_at`을 둔다. 어느 쪽이든 resume할 때 시간을 새로 무제한 부여하지 않는다.

## 오래된 승인과 중복 Resume을 거부한다

Approval decision은 다음 상황에서 stale할 수 있다.

- 사용자가 action을 편집해 새 version이 생성됨
- Run이 Cancel됨
- 다른 reviewer가 먼저 결정함
- Business expiry가 지남
- 새 checkpoint가 이전 interrupt를 대체함

Resume claim은 조건부 update로 하나의 attempt만 이기게 한다.

```sql
UPDATE runs
SET status = 'resuming',
    active_attempt_id = $2,
    active_fence = active_fence + 1
WHERE run_id = $1
  AND status = 'resume_queued'
  AND pending_approval_id = $3
  AND checkpoint_id = $4
RETURNING active_fence;
```

0 row가 반환되면 duplicate 또는 stale resume job이다. Durable state를 다시 읽고 terminal이면 `XACK`, 다른 attempt가 active면 실행하지 않는다.

## 장애 창마다 복구 근거가 있어야 한다

| 장애 창 | 남는 상태 | 복구 방식 |
| --- | --- | --- |
| Checkpoint 저장 후 approval row 전 | interrupt checkpoint만 존재 | Redelivery가 stable ID로 approval upsert |
| Approval row 후 `XACK` 전 | waiting 상태와 pending delivery | Redelivery가 waiting을 확인하고 ack |
| Decision commit 후 Queue publish 전 | approved + outbox | Relay가 resume job 게시 |
| Resume claim 후 Worker crash | active attempt와 pending job | Lease/fence 만료 후 새 attempt reclaim |
| Side effect 후 checkpoint 전 | provider 성공, graph state 이전 | Execution ledger와 idempotency key로 결과 재사용 |

핵심은 memory의 coroutine이나 Worker hostname이 아니라 durable record가 다음 행동을 결정하는 것이다.

## UI는 승인 요청도 snapshot과 event로 복원한다

브라우저가 interrupt 순간에 연결돼 있었다는 보장은 없다. Bootstrap 응답에 현재 pending approval을 포함한다.

```json
{
  "run": {"status": "waiting_approval"},
  "pending_approval": {
    "approval_id": "A17...",
    "action_type": "send_email",
    "action_digest": "8ad1...",
    "expires_at": "2026-10-13T09:00:00Z"
  },
  "cursor": "1731-0"
}
```

Event timeline에는 `approval_requested`, `approval_decided`, `resume_queued`, `run_resumed`를 남긴다. SSE disconnect는 approval 취소가 아니며, 재연결한 UI는 product DB와 event cursor에서 상태를 복원한다.

## 테스트는 pause 사이에 process를 끊어야 한다

In-memory unit test만으로 durability를 증명할 수 없다. 최소한 persistent checkpointer와 product DB를 사용해 다음을 검증한다.

- Interrupt 뒤 Worker를 종료하고 다른 Worker가 같은 checkpoint를 resume
- Approval 생성 전 crash와 stable ID upsert
- `waiting_approval` commit 후 `XACK` 전 crash
- Decision commit 후 outbox publish 전 crash
- 같은 decision 두 번 제출
- 두 reviewer가 동시에 반대 decision 제출
- Action 편집 뒤 이전 digest 승인 거부
- Approval expiry와 Cancel 경쟁
- Resume job 중복 delivery
- Side effect 성공 후 checkpoint 전 crash
- Graph/state schema version 불일치
- SSE 없이 나중에 접속해 pending approval 복원

```python
async def test_resume_does_not_repeat_effect(system):
    run = await system.start_until_interrupt("R1")
    await system.approve(run.pending_approval_id)

    await system.worker.crash_after_tool_success()
    await system.reclaim_and_resume(run.id)

    assert await provider.calls(idempotency_key="R1:send-email") == 1
    assert (await run_store.get(run.id)).status == "succeeded"
```

Assertion은 “checkpoint를 읽었다”가 아니다. **같은 decision이 같은 action에 적용되고, side effect가 한 번이며, 하나의 terminal result로 끝나는가**다.

## 구현 체크리스트

- Checkpoint, run, approval, execution ledger의 책임이 분리되어 있는가?
- `thread_id`와 `run_id` mapping을 durable하게 저장하는가?
- Approval payload에 stable ID, action version과 digest가 있는가?
- Interrupt payload가 작고 JSON-serializable한가?
- `waiting_approval` 전에 checkpoint와 product approval이 durable한가?
- Pause 완료 뒤 현재 Queue entry를 `XACK`하는가?
- Decision과 resume outbox가 같은 transaction에 기록되는가?
- Reviewer의 tenant, role, action scope와 expiry를 검증하는가?
- Resume이 API process가 아니라 새 Worker attempt에서 실행되는가?
- Interrupt 이전 코드가 replay-safe한가?
- 비가역 side effect가 별도 node와 execution ledger로 보호되는가?
- Graph와 state schema version compatibility를 확인하는가?
- Execution budget과 approval business expiry 정책이 분리되어 있는가?
- Duplicate·stale resume이 조건부 update와 fence에서 탈락하는가?

## 재개 가능한 시스템은 이제 전체 궤적을 남겨야 한다

Pause와 resume이 들어오면 하나의 run은 여러 Worker attempt, checkpoint, approval과 tool call에 걸친다. 개별 process log만 보면 “왜 이 action이 두 시간 뒤 실행됐는가”를 설명하기 어렵다.

다음 글에서는 **Agent를 디버깅하는 법: Logs보다 Trajectory가 중요하다**를 통해 run 전체를 trace하고, latency·token·cost·decision·tool result를 하나의 실행 궤적으로 연결하는 observability를 다룬다.
