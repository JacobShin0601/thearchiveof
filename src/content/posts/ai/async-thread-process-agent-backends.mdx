이전 글 [에이전트는 왜 Async가 필요한가](/ai/agents/why-agent-systems-need-async/)에서는 LLM, database, 검색 API의 대기를 겹치는 실행 모델을 살펴봤다. Async는 한 run 안의 독립적인 I/O를 동시에 진행하고, 한 run이 기다리는 동안 다른 run을 진행하게 한다.

그런데 현실의 Agent backend에는 `await`할 수 없는 코드도 들어온다.

- 오래된 Python SDK가 synchronous API만 제공한다.
- PDF parser가 큰 문서를 변환하는 동안 CPU를 계속 사용한다.
- Monte Carlo simulation이 수백만 번의 계산을 수행한다.
- Local embedding이나 LLM inference가 GPU에서 실행된다.

이 작업들을 모두 `async def` 안에 넣는다고 async workload가 되지는 않는다. Event loop thread에서 blocking function을 그대로 호출하면 다른 coroutine까지 멈추고, CPU-bound loop를 thread로 옮긴다고 multi-core 병렬 계산이 자동으로 생기지도 않는다.

핵심은 문법이 아니라 **workload가 어디에서 시간을 쓰는지**다.

## 실행 도구를 고르기 전에 병목을 세 가지로 나눠라

Agent backend의 작업은 먼저 다음 세 범주로 나눌 수 있다.

| Workload | 시간이 사라지는 곳 | 자연스러운 첫 선택 |
| --- | --- | --- |
| Non-blocking I/O | Network, database, queue 응답 대기 | Async I/O |
| Blocking I/O | 동기 SDK가 현재 thread를 점유한 채 대기 | 제한된 thread pool |
| CPU-bound compute | Python code 또는 native code의 실제 계산 | Process, 별도 CPU/GPU service |

이를 실행 구조로 그리면 다음과 같다.

```text
Agent run
   │
   ├─ LLM / PostgreSQL / Redis ── non-blocking wait ──> async task
   │
   ├─ legacy sync SDK ─────────── blocking wait ──────> bounded thread pool
   │
   └─ heavy calculation ───────── CPU execution ─────> process / compute service
```

분류 기준은 library 이름이 아니다. 같은 SDK도 async client와 sync client를 모두 제공할 수 있고, 같은 함수 안에서도 file read는 I/O-bound이지만 parsing은 CPU-bound일 수 있다. 실제 호출 경로를 보고 **무엇을 기다리고, 무엇을 계산하는지**를 판단해야 한다.

## Async: 기다리는 동안 실행권을 돌려준다

Asyncio는 cooperative concurrency다. Coroutine이 non-blocking I/O를 `await`하면 event loop에 실행권을 돌려주고, event loop는 그동안 실행 가능한 다른 task를 진행한다.

```python
import asyncio

async def build_context(query: str):
    llm_task = asyncio.create_task(call_llm(query))
    db_task = asyncio.create_task(query_postgres(query))
    search_task = asyncio.create_task(search_documents(query))

    llm, rows, documents = await asyncio.gather(
        llm_task,
        db_task,
        search_task,
    )
    return {"llm": llm, "rows": rows, "documents": documents}
```

여기서 concurrency가 가능한 이유는 함수 앞에 `async`가 붙었기 때문이 아니다. `call_llm`, `query_postgres`, `search_documents`가 socket 응답을 기다릴 때 thread를 붙잡지 않고 실행권을 양보하기 때문이다.

Async의 비용 모델은 I/O-heavy Agent에 잘 맞는다. Task는 OS thread보다 가볍고, 하나의 event loop가 많은 대기 작업을 관리할 수 있다. 하지만 cooperative하다는 것은 약점이기도 하다. 실행 중인 코드가 실행권을 양보하지 않으면 event loop는 다른 task를 진행할 수 없다.

## `async def` 안의 blocking call은 더 위험하다

다음 함수는 겉으로는 async지만 내부의 SDK가 synchronous라면 event loop를 막는다.

```python
async def enrich_customer(customer_id: str):
    # sync_crm_client.get()이 network response를 기다리는 동안
    # 같은 event loop의 다른 run도 진행하지 못한다.
    profile = sync_crm_client.get(customer_id)
    return await summarize_profile(profile)
```

한 번의 호출이 500ms 걸리면 그 500ms 동안 관계없는 request의 timer, websocket heartbeat, database response 처리까지 지연될 수 있다. 개발 환경에서 사용자가 한 명일 때는 잘 보이지 않지만, concurrent request가 늘면 tail latency가 갑자기 나빠진다.

Library가 async API를 제공한다면 그것을 사용하는 편이 우선이다. 연결 pooling, cancellation, timeout 같은 동작을 event loop와 일관되게 관리할 수 있기 때문이다. Async API가 없고 작업이 blocking I/O라면 thread가 호환성 다리가 될 수 있다.

## Thread: blocking code를 event loop 밖으로 옮기는 호환성 도구

Thread는 한 process 안에서 여러 execution thread를 실행한다. 같은 memory를 공유하므로 object를 process 사이로 직렬화할 필요가 없고, synchronous library를 비교적 작은 변경으로 호출할 수 있다.

Asyncio application에서는 `asyncio.to_thread()`로 blocking function을 별도 thread에서 실행할 수 있다.

```python
import asyncio

def fetch_customer_sync(customer_id: str) -> dict:
    return sync_crm_client.get(customer_id, timeout=5)

async def enrich_customer(customer_id: str):
    profile = await asyncio.to_thread(
        fetch_customer_sync,
        customer_id,
    )
    return await summarize_profile(profile)
```

이제 CRM 호출을 기다리는 동안 event-loop thread는 다른 coroutine을 진행할 수 있다. Python 공식 문서도 `asyncio.to_thread()`를 event loop를 막을 blocking I/O function에 주로 사용하는 방법으로 설명한다. ([Running in Threads](https://docs.python.org/3/library/asyncio-task.html#running-in-threads))

하지만 `to_thread()`는 blocking code를 non-blocking code로 변환하지 않는다. Blocking은 여전히 일어나며, 단지 다른 thread가 그 비용을 맡는다. 그래서 다음 경계가 필요하다.

- 호출 자체에 timeout을 둔다.
- 동시에 실행할 blocking call 수를 제한한다.
- Thread에서 완료된 뒤에는 request-local mutable state를 함부로 공유하지 않는다.
- SDK가 thread-safe인지 확인한다.
- 취소 가능한 awaitable과 실제 thread 작업의 종료를 같은 것으로 가정하지 않는다.

특히 concurrency limit가 중요하다. Request마다 무제한으로 thread를 만들면 외부 API의 rate limit, connection pool, memory를 먼저 소진한다.

```python
import asyncio

blocking_sdk_slots = asyncio.Semaphore(8)

async def call_legacy_sdk(payload: dict) -> dict:
    async with blocking_sdk_slots:
        return await asyncio.to_thread(
            legacy_sdk.execute,
            payload,
        )
```

Thread pool은 압력을 없애지 않는다. Event loop에서 thread queue로 옮길 뿐이다. Pool 크기, timeout, upstream limit를 함께 정해야 backpressure가 생긴다.

## Shared memory는 편리하지만 공짜가 아니다

Thread는 같은 process의 memory를 공유한다. 이 특성은 큰 read-only configuration이나 이미 만들어진 client를 함께 사용할 때 편리하다. 반대로 여러 thread가 같은 mutable object를 수정하면 race condition이 생길 수 있다.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock

results: list[dict] = []
results_lock = Lock()

def collect_one(item: str) -> None:
    result = blocking_lookup(item)
    with results_lock:
        results.append(result)

with ThreadPoolExecutor(max_workers=8) as pool:
    list(pool.map(collect_one, items))
```

이 예시는 lock으로 `results` 수정을 보호하지만, 가능하면 worker thread가 값을 반환하고 한 곳에서 결과를 합치는 구조가 더 단순하다. Shared state가 많아질수록 lock 순서, deadlock, race condition을 추론해야 하기 때문이다.

Agent state를 Python object 하나에 모아 여러 thread가 함께 수정하는 설계는 특히 위험하다. Run state와 event history는 명시적인 owner와 storage boundary를 가져야 한다. 이 시리즈의 state 편에서 그 경계를 다시 다룬다.

## GIL: Thread가 유용하지 않다는 뜻은 아니다

기본 GIL-enabled CPython에서는 한 시점에 하나의 thread만 Python bytecode를 실행할 수 있다. 따라서 pure-Python CPU-bound loop를 thread 여러 개에 나눠도 일반적으로 여러 CPU core를 동시에 활용하는 성능 향상을 기대하기 어렵다. Context switching 비용 때문에 오히려 느려질 수도 있다. Python 공식 문서도 CPU resource를 더 활용하려면 `multiprocessing`이나 `ProcessPoolExecutor`를 고려하고, thread는 I/O-bound task에 여전히 적합하다고 설명한다. ([threading 문서](https://docs.python.org/3/library/threading.html))

그렇다고 "Python thread는 항상 하나씩만 실행된다"고 일반화하면 정확하지 않다.

- Network나 file I/O를 기다리는 동안에는 다른 thread가 진행할 수 있다.
- NumPy 같은 일부 native extension은 계산 중 GIL을 해제할 수 있다.
- Python 3.13부터 GIL을 비활성화할 수 있는 free-threaded build가 제공되지만 기본 build는 아니며, extension compatibility와 실제 workload 측정이 필요하다. ([Free-threading 문서](https://docs.python.org/3/howto/free-threading-python.html))

실무 판단은 더 단순하게 시작해도 된다. **일반적인 GIL-enabled CPython에서 blocking I/O compatibility에는 thread, 무거운 pure-Python 계산에는 process**를 첫 가설로 두고 benchmark로 확인한다.

## Process: 별도 interpreter와 memory로 CPU를 병렬 사용한다

Process는 독립된 Python interpreter와 memory space를 갖는다. 여러 process는 여러 CPU core에서 실제로 동시에 계산할 수 있으므로 pure-Python CPU-bound workload에 적합하다.

다음 예시는 async Agent가 CPU-heavy scoring을 process pool에 넘기는 구조다.

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

PROCESS_POOL = ProcessPoolExecutor(max_workers=4)

def score_scenarios(scenarios: list[dict]) -> list[float]:
    # CPU-bound pure-Python calculation
    return [run_monte_carlo(scenario) for scenario in scenarios]

async def calculate_risk(scenarios: list[dict]) -> list[float]:
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(
        PROCESS_POOL,
        score_scenarios,
        scenarios,
    )
```

Event loop는 process의 계산 결과를 기다리는 동안 다른 I/O task를 진행할 수 있고, CPU 계산은 별도 process에서 실행된다. 다만 process에는 분명한 비용이 있다.

- Process를 시작하고 유지하는 비용이 thread보다 크다.
- Argument와 result는 process boundary를 통과할 수 있도록 직렬화 가능해야 한다.
- 큰 object를 넘기면 serialization과 memory copy 비용이 계산 이익을 상쇄할 수 있다.
- In-memory client, open connection, lock을 아무렇게나 공유할 수 없다.
- Application lifecycle에서 pool 생성과 종료를 명시적으로 관리해야 한다.

따라서 작은 JSON parsing 하나마다 새 process를 띄우는 것은 좋은 선택이 아니다. Process pool을 application lifecycle에 맞춰 재사용하거나, 계산이 충분히 크고 독립적이라면 dedicated CPU worker/service로 분리하는 편이 낫다. `multiprocessing`이 subprocess를 이용해 GIL을 우회할 수 있다는 점과 `ProcessPoolExecutor`의 제약은 Python 공식 문서에도 명시되어 있다. ([multiprocessing](https://docs.python.org/3/library/multiprocessing.html), [concurrent.futures](https://docs.python.org/3/library/concurrent.futures.html))

## Agent backend는 셋을 함께 쓸 수 있다

실제 run은 한 종류의 workload로만 이루어지지 않는다. 하나의 request 안에서 LLM과 database는 async로 기다리고, legacy SDK는 thread로 격리하며, 큰 계산은 process나 별도 service로 보낼 수 있다.

```python
import asyncio

async def execute_agent_run(request: dict) -> dict:
    # 1. Native async I/O: event loop에서 함께 진행한다.
    llm_task = asyncio.create_task(call_llm(request["prompt"]))
    data_task = asyncio.create_task(query_postgres(request["account_id"]))

    # 2. Blocking I/O: 제한된 thread에서 격리한다.
    crm_task = asyncio.create_task(
        call_legacy_sdk({"account_id": request["account_id"]})
    )

    llm, data, crm = await asyncio.gather(
        llm_task,
        data_task,
        crm_task,
    )

    # 3. CPU-bound calculation: process pool에 맡긴다.
    risk = await calculate_risk(build_scenarios(data, crm))

    return compose_answer(llm, data, crm, risk)
```

```text
                         ┌─ LLM API ────────────────┐
                         ├─ PostgreSQL ─────────────┤ async I/O
Request ─> event loop ───┤                          ├─> compose result
                         ├─ legacy SDK ─> thread ───┤
                         └─ risk model ─> process ──┘
```

이 구조에서 event loop가 중심 scheduler 역할을 하지만 모든 일을 직접 실행하지는 않는다. 기다림은 async task로 겹치고, 불가피한 blocking I/O는 bounded thread pool로 격리하며, CPU-heavy work는 process boundary 밖으로 보낸다.

Local LLM inference는 또 다른 경우다. Model weight, batching, GPU memory, kernel scheduling을 관리해야 하므로 web process 안에서 `ProcessPoolExecutor`로 호출하기보다 전용 inference service가 더 자연스러운 경우가 많다. Async Agent는 그 service에 network request를 보내고 결과를 기다린다. Agent 관점에서는 다시 I/O-bound 호출이 된다.

## 선택 기준: library가 아니라 병목부터 본다

| 상황 | 첫 선택 | 이유 | 주의할 점 |
| --- | --- | --- | --- |
| LLM, search API 호출 | Async client | Network 대기를 겹칠 수 있다 | Timeout, rate limit, concurrency cap |
| PostgreSQL, Redis 접근 | Async driver | Socket 대기 중 다른 run 진행 | Connection pool 크기 |
| Sync-only SaaS SDK | Thread offload | Event loop blocking을 격리 | Thread safety, pool saturation |
| File read | Async API 또는 thread | OS/file API 특성에 따라 blocking 가능 | File 수와 descriptor limit |
| 큰 pure-Python 계산 | Process pool | 여러 core에서 병렬 실행 가능 | Serialization, startup, memory |
| NumPy/native 계산 | 측정 후 thread 또는 process | Extension이 GIL을 해제할 수 있다 | Library별 동작과 oversubscription |
| 대규모 Monte Carlo | Dedicated CPU worker | 독립 scaling과 resource control | Queue, result persistence, retry |
| Local LLM inference | GPU inference service | Batching과 GPU lifecycle을 분리 | Admission control, model capacity |

여기서 “첫 선택”은 최종 답이 아니다. Workload를 측정하고, 실제 SDK가 GIL을 해제하는지, data transfer가 얼마나 큰지, downstream limit가 무엇인지 확인해야 한다. 하지만 이 표는 잘못된 출발을 피하게 한다.

## 자주 생기는 다섯 가지 실패

### 1. Blocking SDK를 event loop에서 직접 호출한다

함수 바깥이 `async def`라는 이유로 내부도 non-blocking이라고 착각한다. 결과는 한 요청의 SDK latency가 같은 process의 다른 요청까지 지연시키는 것이다.

### 2. CPU-bound 작업을 thread로 옮기고 scale-out을 기대한다

기본 CPython에서 pure-Python 계산이라면 GIL 때문에 원하는 multi-core 병렬성이 나오지 않을 가능성이 크다. Thread offload가 event loop responsiveness는 지킬 수 있어도 계산량 자체를 빨리 끝내주지는 않는다.

### 3. 짧은 I/O마다 process를 사용한다

Process boundary의 startup, IPC, serialization 비용이 실제 작업보다 커진다. I/O 대기는 async나 thread가 더 자연스럽다.

### 4. Shared mutable state를 보호 없이 여러 thread가 수정한다

우연히 테스트가 통과해도 production concurrency에서 state corruption이나 재현하기 어려운 race가 나타날 수 있다. 값을 반환해 한 owner가 합치거나, 불가피하면 명시적인 synchronization을 둔다.

### 5. Web request마다 process pool을 새로 만든다

Traffic과 함께 process 수가 폭증하고 memory가 중복된다. Pool은 application lifecycle에서 관리하거나, 큰 작업은 queue 뒤의 dedicated compute worker가 소유하게 해야 한다.

## Async, thread, process는 lifecycle owner가 아니다

여기까지의 세 도구는 주로 **어떻게 동시에 진행하거나 병렬 실행할지**에 답한다.

- Async task는 event loop 안에서 I/O 대기를 겹친다.
- Thread는 같은 process 안에서 blocking call을 격리한다.
- Process는 별도 interpreter와 memory에서 계산을 실행한다.

하지만 production Agent에는 다른 질문이 남는다.

- HTTP request가 끊겨도 5분짜리 run은 계속되어야 하는가?
- Process가 죽으면 누가 미완료 작업을 다시 가져가는가?
- Retry 중인 run의 상태와 progress는 어디에 저장하는가?
- 같은 session에서 동시에 들어온 두 run을 어떻게 제한하는가?
- 배포 중에도 진행 중인 작업을 안전하게 끝낼 수 있는가?

이 질문은 `async`, `thread`, `process` 중 무엇을 고를지로 답할 수 없다. 이것은 **execution lifecycle을 누가 소유하는가**의 문제다.

```text
Concurrency primitive                     Lifecycle ownership
──────────────────────────────────         ─────────────────────────────
async / thread / process                   API process / queue / worker
"어떻게 진행하고 계산하는가?"              "누가 끝까지 책임지는가?"
```

Worker는 thread의 다른 이름도, process의 동의어도 아니다. Worker process 하나가 내부에서 asyncio event loop를 실행하고, blocking SDK를 thread pool로 보내며, CPU calculation을 별도 process나 compute service에 위임할 수 있다.

> 어떻게 동시에 실행하나와 누가 이 작업의 lifecycle을 소유하나는 다른 질문이다.

다음 글 **A Worker Is Not a Thread**에서는 API process와 execution process를 왜 분리하는지, worker가 왜 concurrency primitive가 아니라 lifecycle ownership boundary인지 살펴본다.
