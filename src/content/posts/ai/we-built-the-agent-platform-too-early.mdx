<AnswerBlock question="좋은 Enterprise Agent Platform은 어떻게 만들어야 할까?">
  좋은 에이전트 플랫폼은 화이트보드에서 먼저 완성되는 것이 아니다. 하나의 좁은 문제를 실제 업무에 배포하고, 실패를 관찰하고, 고치고, 같은 문제가 반복되는 것을 확인한 뒤에야 공통 기능을 추출할 수 있다. 코딩 에이전트는 그럴듯한 프로토타입을 만드는 비용을 크게 낮췄지만, 평가·권한·상태·복구·관측·보안·운영의 비용까지 없애지는 않았다. <strong>플랫폼을 먼저 상상하기보다 Experienced → Repeated → Abstracted의 순서로 획득해야 한다.</strong>
</AnswerBlock>

사내에서 들어오는 AI 요구를 모아 보면 서로 달라 보이는 요청들이 비슷한 구조로 수렴했다.

1. 복잡한 기업 내부 문서를 이해한다.
2. 외부의 시장·경쟁사·재무 정보를 결합한다.
3. 특정 분석 framework를 적용해 insight를 만든다.

예를 들어 내부 사업계획, 경쟁사 실적, 시장 데이터를 모아 3C 분석을 만드는 식이다. 분석 대상과 산출물은 달라도 필요한 능력은 상당 부분 겹쳤다. 그렇다면 공통 능력을 재사용 가능한 building block으로 만들고, 사용자가 직접 조합하게 하면 되지 않을까?

이 생각은 자연스럽게 플랫폼으로 이어졌다.

<AgentPlatformDiagrams kind="platform" id="composable-platform" caption="Tools, Modules, Agent Runs, Dynamic Orchestration으로 이어지는 composable enterprise agent architecture. 당시 왜 플랫폼 접근이 합리적이었는지를 보여준다." />

가장 아래에는 개발자가 제공하는 **Tool**이 있다. 내부 문서 검색, 웹 검색, 데이터베이스 조회, Python 실행, 외부 API, 금융 데이터, 사내 시스템 연동 같은 capability다.

그 위에는 사용자가 여러 Tool과 작업 지침을 묶어 만드는 **Module**이 있다. 예를 들어 내부 검색, 시장 검색, 경쟁사 검색에 분석 지침을 더하면 ‘3C Analysis Module’이 된다. Module은 단순히 저장된 prompt가 아니라 특정 목적을 수행하기 위한 reusable business capability다.

여러 Module을 연결하면 **Agent Run**이 된다. 시장 조사 → 경쟁사 분석 → 내부 역량 분석 → 종합처럼 순차 실행할 수도 있고, specialist agent들을 병렬로 실행한 뒤 synthesis agent가 결과를 합칠 수도 있다.

마지막에는 **Dynamic Orchestration**이 있다. 사용자가 복잡한 질문을 입력하면 시스템이 문제를 분해하고, 필요한 Module과 Tool을 찾고, dependency를 판단해 sequential·parallel workflow 또는 multi-agent DAG를 runtime에 구성한다.

> Build once, compose many workflows.

개념적으로 꽤 합리적인 architecture였다. 여러 요구를 각각 별도의 application으로 만드는 대신, 공통 능력을 한 번 개발하고 다양한 업무에 조합할 수 있었다. 새로운 요구에도 빠르게 대응할 수 있고 사용자에게 일정한 자율성을 줄 수 있었다. 당시 이 선택이 잘못된 것은 아니었다. 다만 production이 우리에게 아직 알려주지 않은 것이 너무 많았다.

## 프로토타입이 너무 그럴듯해진 시대

지금은 Claude Code, Cursor, Codex 같은 코딩 에이전트가 파일을 읽고 수정하며, 명령을 실행하고, 테스트를 돌리고, 비교적 큰 작업까지 이어서 수행한다. 각 제품의 공식 설명도 이들을 단순 자동완성이 아니라 복잡한 개발 작업을 수행하는 agent로 규정한다. 덕분에 문서를 읽고, 검색하고, tool을 호출하고, multi-agent orchestration을 수행하며, polished UI까지 갖춘 AI application을 며칠 안에 만드는 일이 가능해졌다.

이것은 분명한 기술 진보다. 문제는 성공의 외형도 함께 압축됐다는 데 있다.

이제 프로토타입은 예전의 프로토타입처럼 보이지 않는다. 데모는 실제 데이터를 읽고, 자연어로 계획을 설명하고, 여러 시스템을 오가며, 완성도 높은 화면에 결과를 표시한다. 기술을 직접 만들지 않은 사람의 눈에는 이미 제품처럼 보인다. Management가 비합리적이어서가 아니다. 화면에 보이는 신호 대부분이 ‘거의 완성됐다’고 말하기 때문이다.

나는 이것을 **The Prototype Illusion**, 즉 프로토타입의 착시라고 부른다.

<AgentPlatformDiagrams kind="illusion" id="prototype-illusion" caption="Visible capability는 빠르게 완성돼 보이지만 production readiness는 훨씬 긴 tail을 가진다. 두 곡선 사이가 Demo-to-Production Gap이다." />

초기의 visible capability는 아주 빠르게 상승한다. 모델을 연결하고, prompt를 쓰고, tool calling을 붙이고, UI를 다듬으면 짧은 시간 안에 놀라운 결과가 나온다. 하지만 production readiness의 곡선은 훨씬 완만하다. 평가, 권한, 보안, 상태 관리, 장애 복구, latency, monitoring, audit, 운영 프로세스, 그리고 신뢰는 긴 꼬리를 가진다.

그래서 지금의 핵심 문장은 이것이다.

> **AI coding has compressed the cost of building demos, not the cost of operating systems.**

코딩 에이전트는 구현 비용을 크게 낮춘다. 하지만 그 시스템이 실제 업무에서 매일 같은 수준으로 작동하도록 만드는 비용은 다른 종류의 비용이다. 두 곡선 사이의 간격이 바로 **Demo-to-Production Gap**이다.

## 어려운 문제는 architecture보다 predictability였다

플랫폼이 production에 가까워질수록 어려움의 중심은 ‘무엇을 할 수 있는가’에서 ‘어떻게 예측 가능하게 할 것인가’로 이동했다.

예를 들어 tool selection 하나만 해도 그렇다. 같은 질문인데 왜 어떤 run에서는 내부 검색을 먼저 하고, 다른 run에서는 웹 검색부터 시작하는가? Tool 설명을 고치면 선택은 나아지지만 다른 use case의 routing이 망가질 수 있다. Model version이 바뀌면 이전에 안정적이던 경계가 다시 흔들린다.

Decomposition에도 분산이 생긴다. 어떤 run은 문제를 세 단계로 나누고, 어떤 run은 일곱 단계로 나눈다. 각각의 subtask는 그럴듯해도 순서와 dependency가 달라지면 최종 결과가 달라진다. 여기에 context loss와 intermediate hallucination이 더해진다. 앞 단계의 작은 오류가 다음 agent에게 사실처럼 전달되면, 뒤의 agent는 잘못된 전제 위에서 더 정교한 결론을 만든다.

연결은 또 다른 문제였다. Module A와 B를 각각 테스트하면 잘 작동하는데, A의 출력을 B의 입력으로 연결하면 품질이 떨어졌다. A가 사람에게는 충분히 읽히지만 B가 기대하는 schema에는 맞지 않을 수 있다. B가 A의 uncertainty를 전달받지 못할 수도 있다. 각 node의 품질만으로 전체 workflow의 품질을 보장할 수 없었다.

실패 복구는 더 까다롭다.

- Tool 하나가 timeout이면 그 node만 재시도할 것인가, planning부터 다시 시작할 것인가?
- 부분 retry 뒤에 이미 생성된 state를 유지할 것인가, 폐기할 것인가?
- 외부 API 호출이 실제로 실행됐지만 응답만 유실됐다면 재호출해도 되는가?
- 병렬 branch 중 하나가 실패했을 때 나머지 결과로 계속 진행할 것인가?
- 잘못된 intermediate answer가 다음 단계로 전파되는 것을 어디에서 차단할 것인가?

여기에 authentication, authorization, logging, observability, output validation, document format variance, API failure, model change가 겹친다. 질문 하나에 답하는 데 필요한 자유도를 높일수록 capability는 커지지만 가능한 failure mode의 조합도 함께 늘어난다.

결국 가장 어려운 질문은 하나였다.

> **How do you make an agent predictable?**

우리 시스템은 약 3개월 동안 실제 사용과 실패, 수정의 반복을 거치면서 상당히 안정화됐다. 안정성은 처음 그린 architecture에서 나온 것이 아니라, 어떤 실패가 실제로 반복되는지를 알게 된 뒤 추가한 작은 제약과 복구 장치들의 합에서 나왔다.

## 사용자는 우리의 architecture를 경험하지 않는다

개발자는 시스템이 왜 어려운지 안다. 복잡한 사내 권한을 지키면서 여러 문서 형식을 처리하고, 외부 데이터와 내부 시스템을 연결하며, 긴 workflow의 state를 유지하는 일이 얼마나 까다로운지 안다.

하지만 사용자는 그 복잡도를 평가하지 않는다. 사용자가 비교하는 것은 다른 사내 시스템이 아니라 ChatGPT와 Claude다.

내부 Agent가 더 어려운 문제를 다루고 있더라도, 이상한 답을 한 번 내거나, 지나치게 느리거나, 같은 질문의 결과가 크게 달라지거나, 엉뚱한 Tool을 선택하거나, 이유를 알 수 없는 행동을 하면 평가는 간단하다.

“아직 잘 안 된다.”

이 평가는 불공정하지 않다. 사용자는 architecture diagram이 아니라 업무 경험을 평가하기 때문이다.

> **Users do not experience your architecture. They experience your failures.**

기업 Agent에는 일반 chatbot보다 많은 제약이 있다. 내부 시스템과 연결돼야 하고, 사용자의 permission을 따라야 하며, 기업 문서를 이해하고, business workflow를 실행해야 한다. 반면 interaction quality에 대한 benchmark는 이미 세계 최고 수준의 consumer AI가 만들어 놓았다. 이 둘의 간극을 좁히는 것이 enterprise agent engineering의 상당 부분이다.

## 수면 아래의 마지막 10%

데모에서 눈에 띄는 것은 model, prompt, tool calling, search, agent reasoning, multi-agent collaboration, UI다. 이 요소들이 실제로 중요하지 않다는 뜻은 아니다. 다만 production에서 살아남는 조건은 대체로 수면 아래에 있다.

<AgentPlatformDiagrams kind="iceberg" id="agent-iceberg" caption="데모를 인상적으로 만드는 것은 수면 위에 있다. 시스템이 실제 업무에서 살아남게 만드는 것은 수면 아래에 있다." />

평가 체계가 없으면 개선인지 regression인지 알 수 없다. Observability가 없으면 실패했다는 사실은 알아도 어디에서 왜 실패했는지 모른다. Authorization이 허술하면 좋은 답을 내는 것 자체가 사고가 될 수 있다. Retry policy가 없으면 일시적 장애가 전체 실패가 되고, 잘못 설계하면 같은 외부 작업을 두 번 실행한다. Human escalation이 없으면 시스템이 모르는 것을 모른다고 말해도 업무가 끝나지 않는다.

이 때문에 나는 다음 표현을 쓴다.

> **The last 10% of engineering can determine 90% of perceived reliability.**

이 숫자는 측정된 통계가 아니라 강조를 위한 표현이다. 요점은 데모의 마지막 부분처럼 보이는 운영·통제 계층이 사용자가 체감하는 신뢰도의 대부분을 결정할 수 있다는 것이다.

## 너무 이른 공개가 만든 Trust Debt

내부 일정과 management timeline 때문에 시스템은 충분히 성숙하기 전에 비교적 넓은 사용자에게 공개됐다. 기술적으로는 작동했지만 우리가 원하는 reliability에는 아직 도달하지 못한 상태였다.

그 결과 초기 사용자 중 상당수가 이탈했다. 이후 품질을 안정화하고 UX를 개선하고 적합한 use case를 다시 발굴했지만, 사용자를 되돌리는 일은 처음 사용자를 모으는 일보다 어려웠다.

이 경험을 나는 **Trust Debt**라고 정리한다.

Technical debt는 빠른 구현을 위해 미래의 engineering cost를 빌려오는 일이다. Trust debt는 성숙하지 않은 경험을 넓게 노출해 미래의 adoption cost를 빌려오는 일이다.

AI 시스템의 신뢰는 대칭적으로 움직이지 않는다. 몇 번 좋은 결과가 나왔다고 바로 중요한 업무를 맡기지는 않는다. 반면 중요한 순간에 크게 실패하면 사용자는 빠르게 돌아선다. 이후 시스템이 실제로 좋아져도 “예전에 써 봤는데 안 됐다”는 기억이 새로운 평가보다 먼저 작동한다.

그래서 rollout은 단순한 배포 범위의 문제가 아니다. 학습 속도와 신뢰 보존 사이의 설계다. 좁은 문제와 제한된 사용자로 시작해 실패를 가까이에서 관찰하면 feedback을 얻으면서도 신뢰 손실의 blast radius를 줄일 수 있다. 반대로 넓은 공개는 많은 feedback을 주지만, 아직 모르는 failure mode까지 한꺼번에 사용자에게 노출한다.

## 플랫폼을 먼저 만들지 않는다는 것

처음의 사고 순서는 이랬다.

**Many Requirements → Common Abstraction → Platform → Many Use Cases**

여러 요구에서 공통점을 관찰하고, abstraction을 설계하고, 플랫폼을 만든 뒤 다양한 use case를 태우는 방식이다. 논리적이지만 한 가지 취약점이 있다. 공통적으로 *말해진 요구*와 production에서 *반복되는 문제*는 같지 않을 수 있다.

지금 다시 한다면 순서를 바꿀 것이다.

<AgentPlatformDiagrams kind="sequence" id="platform-vs-production" caption="Platform First는 경험 전에 abstraction을 상상한다. Production First는 반복되는 failure와 fix에서 building block을 추출한다." />

예를 들어 “전략 보고서를 작성하는 AI Agent”처럼 넓게 시작하지 않는다. 다음 정도까지 줄인다.

> 내부 사업계획과 지정된 경쟁사 5곳의 최신 실적을 읽어, 정해진 template의 3C 분석을 생성한다.

Data source를 제한한다. Tool을 제한한다. Output schema를 고정한다. Agent autonomy도 제한한다. 사용자가 어떤 결정을 내리기 위해 결과를 쓰는지 정의하고, 그 하나를 production 수준까지 가져간다.

첫 번째 use case에서 생긴 문제를 모두 플랫폼 기능으로 만들지도 않는다. 일부는 그 업무만의 예외일 수 있기 때문이다. 두 번째 use case에서도 같은 문제가 나타나는지 본다. 세 번째에서도 반복될 때 비로소 common capability로 추출한다.

> **Experienced → Repeated → Abstracted**

이 순서는 abstraction을 포기하자는 말이 아니다. Abstraction의 증거 기준을 높이자는 말이다.

예를 들어 세 use case가 모두 “승인된 source만 검색해야 한다”는 문제를 가진다면 permission-aware retrieval은 building block이 될 수 있다. 세 use case가 모두 장시간 workflow의 중간 결과를 검증하고 재개해야 한다면 durable state와 checkpoint가 공통 계층이 될 수 있다. 반면 한 업무에서만 필요한 특수한 보고서 구조를 범용 Module 규격에 밀어 넣으면 플랫폼 전체가 예외 처리로 부풀어 오른다.

핵심은 이것이다.

> **The right abstraction should be discovered, not imagined.**

## Wonderful에서 발견한 비슷한 관찰

이 결론을 먼저 경험으로 얻은 뒤, Wonderful의 글들에서 비슷한 관찰을 발견했다. Wonderful은 enterprise AI platform을 판매하는 commercial vendor다. 따라서 그들이 제시하는 “무엇을 사고 무엇을 만들 것인가”의 결론은 positioning과 분리해서 읽어야 한다. 그럼에도 production learning에 관한 관찰은 내 경험과 놀랄 만큼 겹친다.

[「The Hard Part of AI Agents Isn’t Building Them」](https://www.wonderful.ai/blog-articles/the-hard-part-of-ai-agents-isn%E2%80%99t-building-them)은 agent를 만드는 도구보다 안전하게 운영하는 도구가 더 부족하다고 지적한다. 실서비스에서는 배포 전 behavior verification, 대규모 failure detection, 실시간 compliance enforcement, 운영 상태 monitoring, regression 없는 지속 개선이 필요하다는 것이다. 이것은 capability보다 predictability가 더 어려웠다는 내 경험과 맞닿는다.

[「Why enterprise AI gets stuck in pilot mode」](https://www.wonderful.ai/blog-articles/why-enterprise-ai-gets-stuck-in-pilot-mode)는 prototype이 쉬워진 것이 legacy integration, scale에서 드러나는 edge case, 운영 의사결정의 난도를 가린다고 주장한다. 또한 agent를 한 번 출시하고 끝나는 제품이 아니라 model, orchestration, data integration, policy가 계속 변하는 living system으로 본다. Production을 도착점이 아니라 반복이 시작되는 지점으로 본다는 점이 중요하다.

[「The Learning Curve You Can’t Skip」](https://www.wonderful.ai/blog-articles/the-learning-curve-you-can%E2%80%99t-skip)은 prompt와 code만으로 좋은 agent를 만들 수 없으며 production에서 실패를 보고 고치는 경험이 필요하다고 말한다. 이 글에서 가장 설득력 있는 부분은 노하우가 문서보다 사람의 머릿속과 수많은 수정에 축적된다는 관찰이다. 우리가 약 3개월의 반복 끝에 얻은 것도 처음 설계할 때 알 수 없었던 이런 tacit knowledge였다.

[「The Execution Gap No Model Can Close」](https://www.wonderful.ai/blog-articles/the-execution-gap-no-model-can-close)는 병목이 model capability만이 아니라 실제 workflow, 언어, 시스템, 규제, 문화 안에 AI를 심는 implementation에 있다고 본다. 모델이 좋아지면 일부 failure mode는 줄어들겠지만, 권한의 source of truth나 조직의 escalation rule 같은 문제는 더 큰 모델이 대신 결정해 주지 않는다.

[「Building an AI Platform Won’t Transform Your Business」](https://www.wonderful.ai/blog-articles/building-an-ai-platform-won%E2%80%99t-transform-your-business)는 기업이 자기 사업에 고유한 agent 대신 orchestration, evaluation, observability, governance, model routing 같은 범용 인프라를 계속 만들게 되는 함정을 지적한다. 여기서 Wonderful은 인프라를 사고 agent를 만들라는 vendor의 결론으로 나아간다. 나는 그 결론을 보편 법칙으로 받아들이지는 않는다. 규제, sovereignty, 차별화, 기존 역량에 따라 build/buy 경계는 달라진다. 다만 플랫폼 자체가 transformation은 아니며, 범용 계층을 유지하는 일이 독립된 장기 제품 책임이라는 지적에는 동의한다.

가장 직접적으로 연결되는 글은 2026년 9월 17일의 [「Let the Field Build the Product」](https://www.wonderful.ai/blog-articles/let-the-field-build-the-product)다. Wonderful은 FDE가 고객 현장에서 성능 문제나 파일 업로드 실패를 발견하고 직접 수정한 뒤, 그 해결책이 플랫폼으로 돌아가 다음 배포의 출발점을 높이는 loop를 설명한다.

**Deployment → Failure → Fix → Productization → Better Next Deployment**

이것이 내가 말하는 “Earn the Platform”과 가장 가깝다. 플랫폼은 현장 배포 뒤에 놓인 별도 단계가 아니다. 배포에서 얻은 반복 가능한 학습이 플랫폼을 만든다.

## 그렇다면 플랫폼은 언제 만들어야 하는가

“플랫폼을 먼저 만들지 말라”는 말이 플랫폼 팀을 없애거나 모든 use case를 일회성으로 만들라는 뜻은 아니다. 공통 기반이 반드시 필요한 경우도 있다. 인증, 감사, 데이터 경계, 배포 표준처럼 기업 전체가 처음부터 지켜야 하는 constraint는 첫 use case 전에도 설계해야 한다.

다만 처음부터 완성해야 하는 것은 **minimum viable control plane**이지, 미래의 모든 workflow를 표현할 수 있는 universal abstraction이 아니다.

플랫폼으로 추출할 시점을 판단할 때는 다음 질문이 유용하다.

1. 이 문제가 서로 다른 use case에서 실제로 반복됐는가?
2. 반복된 문제의 원인이 정말 같은가, 표면만 비슷한가?
3. 공통화하면 각 use case의 품질과 속도가 좋아지는가?
4. Abstraction을 유지할 owner와 운영 비용이 있는가?
5. 예외가 생겼을 때 플랫폼을 우회할 escape hatch가 있는가?

세 번의 반복이 마법의 숫자는 아니다. 중요한 것은 abstraction의 근거가 사전 추측이 아니라 관찰된 production evidence라는 점이다.

## Production Before Platform

처음에는 기업의 수많은 AI 요구사항을 하나의 플랫폼에서 해결하고 싶었다. 그 목표는 여전히 매력적이고, 어떤 부분은 실제로 유효했다. 하지만 플랫폼의 모양을 가장 정확히 알려주는 것은 요구사항 목록이 아니라 production에서 반복되는 실패였다.

지금 다시 시작한다면 하나의 문제를 선택할 것이다.

그리고 그 하나를 끝까지 해결할 것이다.

두 번째 문제에서 반복되는 것을 찾을 것이다.

세 번째에서도 반복된다면 비로소 abstraction으로 만들 것이다.

그리고 그때야 그것을 platform이라고 부를 것이다.

> **Don’t start by building the platform. Earn the platform through production.**

## Key Takeaways

- 코딩 에이전트는 데모 구현 비용을 낮췄지만, production 운영 비용까지 없애지는 않았다.
- Enterprise agent의 핵심 난제는 capability보다 predictability다.
- 사용자는 architecture의 복잡성이 아니라 실패의 빈도와 복구 경험으로 시스템을 평가한다.
- 넓고 이른 공개는 technical debt와 별개로 adoption을 늦추는 Trust Debt를 만들 수 있다.
- 좋은 abstraction은 요구사항 회의에서 상상하기보다 서로 다른 production use case에서 반복되는 문제로부터 추출해야 한다.
- 먼저 필요한 것은 universal platform이 아니라 좁은 use case와 minimum viable control plane이다.
- 플랫폼은 배포의 전제라기보다 **Production → Learning → Repetition → Productization**의 결과물에 가깝다.
