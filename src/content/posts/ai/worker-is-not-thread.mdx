<AnswerBlock question="Agent backend에서 worker란 무엇인가?">
  Worker는 thread나 process 같은 concurrency primitive가 아니라 <strong>workload의 execution lifecycle을 맡는 역할</strong>이다. API가 요청을 검증하고 실행을 접수한다면, worker는 queue에서 작업을 가져와 상태를 갱신하고, 완료·실패·재시도 가능한 결과가 남을 때까지 active attempt를 소유한다. Worker process 내부에서는 다시 async, thread, process를 조합할 수 있다.
</AnswerBlock>

이전 글 [Async, Thread, Process](/ai/agents/async-thread-process-agent-backends/)에서는 workload의 병목에 따라 실행 도구를 나눴다.

- Non-blocking I/O에는 async
- Blocking I/O에는 제한된 thread offload
- CPU-bound 계산에는 process나 별도 compute service

그다음 흔히 이런 질문이 나온다.

> 그러면 worker는 process인가? Thread pool의 thread 하나를 worker라고 부르는 것인가?

둘 다 가능하지만 핵심을 놓친 질문이다. Thread와 process는 **코드가 어떻게 실행되는가**를 설명한다. Worker는 **누가 작업을 가져가고, 진행 상태와 실패를 관리하며, 언제 책임을 내려놓는가**를 설명한다.

```text
Execution mechanism                       Workload ownership
───────────────────────────────           ─────────────────────────────
async task / thread / process             API / queue / worker
어떻게 동시에 진행·계산하는가?             누가 lifecycle을 책임지는가?
```

이 둘을 같은 축의 선택지로 놓으면 Agent backend의 중요한 failure mode를 놓치게 된다.

## 가장 짧은 구현: API에서 background task를 만든다

Agent run을 비동기로 시작하는 가장 간단한 코드는 다음과 같다.

```python
import asyncio
from fastapi import FastAPI

app = FastAPI()

@app.post("/analysis", status_code=202)
async def start_analysis(request: AnalysisRequest):
    run_id = new_run_id()
    asyncio.create_task(run_analysis(run_id, request))
    return {"run_id": run_id, "status": "started"}
```

Endpoint는 즉시 `202 Accepted`를 반환하고 coroutine은 같은 event loop에서 계속 실행된다. Demo에서는 잘 작동한다. 하지만 HTTP response를 먼저 반환했다고 작업이 durable해진 것은 아니다.

이 task의 실제 owner는 API process다.

```text
API process
   ├─ HTTP request handler ──> 202 Accepted
   └─ asyncio task ──────────> long-running analysis

API process 종료
   └─ task도 함께 종료
```

Rolling deployment, out-of-memory termination, application crash, container restart가 발생하면 in-memory task도 함께 사라질 수 있다. 사용자는 이미 `run_id`를 받았지만 그 run을 다시 발견하거나 이어갈 durable owner가 없다.

Python의 `asyncio.create_task()`는 현재 event loop에 coroutine을 schedule하는 API다. 공식 문서는 background task가 실행 중 사라지지 않도록 reference를 보관하고, 완료된 task의 exception도 회수해야 한다고 명시한다. ([Coroutines and Tasks](https://docs.python.org/3/library/asyncio-task.html#creating-tasks)) 이 규칙을 지켜도 **process failure를 넘어서는 durability**까지 생기지는 않는다.

```python
background_tasks: set[asyncio.Task] = set()

def start_local_task(coroutine) -> None:
    task = asyncio.create_task(coroutine)
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)
```

이 코드는 task reference 관리 문제를 해결할 뿐이다. API process가 종료되면 set과 task가 모두 사라진다.

## In-process background task가 항상 나쁜 것은 아니다

API process에서 response 이후 작업을 실행하는 것 자체가 잘못은 아니다. FastAPI도 `BackgroundTasks`를 제공하며, 작은 post-response 작업에는 유용하다고 설명한다. 같은 공식 문서는 여러 process나 server에서 실행할 무거운 background computation이라면 queue를 사용하는 더 큰 도구가 적합할 수 있다고 구분한다. ([FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/))

In-process task는 다음 조건에서 합리적일 수 있다.

- 실행 시간이 짧다.
- 실패하면 다음 request에서 다시 계산해도 된다.
- 결과를 durable하게 추적할 필요가 없다.
- 중간 progress나 cancellation을 제공하지 않는다.
- 배포 중 유실되어도 business impact가 작다.

예를 들어 best-effort cache warming이나 중요하지 않은 telemetry flush는 이 범주에 들어갈 수 있다. 반대로 다음 조건이 하나라도 중요하면 ownership을 process 밖으로 옮기는 편이 자연스럽다.

- 사용자가 `run_id`로 상태와 결과를 다시 조회해야 한다.
- 수십 초에서 수분 이상 실행될 수 있다.
- 실패 시 retry하거나 다른 worker가 회수해야 한다.
- Side effect가 있어 중복 실행을 제어해야 한다.
- API와 다른 CPU, memory, GPU profile로 scale해야 한다.
- Client disconnect와 무관하게 실행을 계속해야 한다.

경계는 특정 시간 숫자 하나로 정해지지 않는다. 5초짜리 결제 작업은 durable ownership이 필요할 수 있고, 30초짜리 재생성 가능한 preview는 요청 안에서 기다려도 될 수 있다. 핵심은 latency가 아니라 **유실과 중복 실행을 시스템이 어떻게 다뤄야 하는가**다.

## Queue는 실행의 접수 기록을 process 밖에 남긴다

API와 worker 사이에 queue를 두면 execution request가 특정 API process의 memory에서 벗어난다.

```text
Client
  │ POST /runs
  ▼
API ── validate / authorize / create run ──> Queue
  │                                           │
  └────────── 202 + run_id                    ▼
                                              Worker
                                                │
                                                ├─ claim work
                                                ├─ execute agent
                                                ├─ update progress
                                                ├─ persist result
                                                └─ acknowledge
```

API process가 response 직후 재시작되어도 queue에 제출된 작업은 다른 consumer가 가져갈 수 있다. 물론 queue라는 상자를 그렸다고 모든 failure가 해결되는 것은 아니다. Durable submission, claim/lease, acknowledgement, retry, dead-letter policy가 실제로 설계되어야 한다.

API의 책임은 실행 자체보다 **안전하게 접수하는 것**에 가까워진다.

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.post("/runs", status_code=202)
async def create_run(request: RunRequest, user: User = Depends(current_user)):
    authorize(user, request)
    validated = validate_run_request(request)
    run_id = new_run_id()

    await run_store.create(
        run_id=run_id,
        user_id=user.id,
        status="submitting",
        input=validated,
    )

    try:
        await job_queue.publish(
            {"run_id": run_id, "input": validated}
        )
    except Exception:
        await run_store.mark_submission_failed(run_id)
        raise HTTPException(503, "Could not submit run")

    await run_store.mark_queued(run_id)
    return {"run_id": run_id, "status": "queued"}
```

이 예시는 ownership handoff를 보여주기 위한 최소 구조다. Database write에는 성공했지만 queue publish 직전에 process가 죽는 dual-write failure까지 원자적으로 해결하지는 않는다. Production에서는 transactional outbox처럼 접수 기록과 publish를 연결하는 방법이나, queue 자체를 authoritative source로 삼는 방법이 필요하다. 중요한 것은 `202`를 반환하기 전에 시스템이 **나중에 다시 발견할 수 있는 실행 의도**를 남기는 것이다.

## Worker는 active attempt의 lifecycle을 소유한다

Worker는 queue에서 message를 읽는 process라는 구현 형태보다 그 message를 받은 뒤 수행하는 책임으로 정의하는 편이 정확하다.

```text
queued
  │ claim
  ▼
claimed ──> running ──> result persisted ──> acknowledged
                 │
                 └────> failed / retryable / terminal
```

일반적인 worker의 책임은 다음과 같다.

1. 실행 가능한 작업을 claim한다.
2. Run과 attempt 상태를 `running`으로 전환한다.
3. Agent graph와 tool orchestration을 실행한다.
4. Progress와 event를 외부 storage에 기록한다.
5. 결과 또는 terminal failure를 durable하게 저장한다.
6. 저장이 끝난 뒤 queue message를 acknowledge한다.

Plain Python으로 표현하면 핵심 순서는 다음과 같다.

```python
async def handle_message(message: JobMessage) -> None:
    run_id = message.run_id
    attempt_id = await run_store.start_attempt(run_id)

    try:
        result = await execute_agent(
            run_id=run_id,
            payload=message.payload,
        )
        await run_store.complete_attempt(
            run_id=run_id,
            attempt_id=attempt_id,
            result=result,
        )
    except RetryableError as error:
        await run_store.record_retryable_failure(
            run_id, attempt_id, error
        )
        await message.retry()
        return
    except Exception as error:
        await run_store.fail_attempt(
            run_id, attempt_id, error
        )
    finally:
        await release_run_resources(run_id)

    # Terminal result가 durable하게 기록된 뒤에만 완료 처리한다.
    await message.ack()
```

이 코드도 queue 제품별 의미를 생략한 conceptual example이다. 일부 queue에서는 retry가 negative acknowledgement이고, 일부에서는 visibility timeout이나 pending entry reclaim으로 구현된다. 그 차이는 Article 10 **When Workers Die**에서 다룬다.

여기서 중요한 순서는 `execute → persist terminal state → acknowledge`다. 먼저 acknowledge한 뒤 result 저장에 실패하면 queue에는 완료된 것으로 보이지만 사용자는 결과를 찾을 수 없다. 반대로 result를 저장하고 acknowledge 직전에 worker가 죽으면 같은 message가 다시 전달될 수 있다. 그래서 worker architecture는 **at-least-once delivery와 idempotency 문제를 없애는 것이 아니라 드러낸다.** Exactly-once처럼 보이는 user experience를 만들려면 run identity, attempt identity, idempotent side effect가 필요하다.

## Worker 하나가 job 하나만 실행해야 하는 것은 아니다

Worker를 OS thread 하나와 동일시하면 worker process 안의 concurrency를 설계하기 어렵다. I/O-heavy Agent라면 worker process 하나가 asyncio event loop를 실행하면서 여러 job을 제한된 수만큼 진행할 수 있다.

```text
Worker process
   └─ asyncio event loop
        ├─ run A ── await LLM ────── resume
        ├─ run B ── await DB ─────── resume
        └─ run C ── await search ─── resume
```

동시 실행 수에는 반드시 상한이 있어야 한다. Queue에 message가 많다는 이유로 모두 task로 만들면 LLM rate limit, database connection pool, memory가 먼저 고갈된다.

```python
import asyncio

MAX_IN_FLIGHT = 8

async def worker_main() -> None:
    in_flight: set[asyncio.Task] = set()

    while True:
        while len(in_flight) < MAX_IN_FLIGHT:
            message = await job_queue.receive()
            task = asyncio.create_task(handle_message(message))
            in_flight.add(task)

        done, in_flight = await asyncio.wait(
            in_flight,
            return_when=asyncio.FIRST_COMPLETED,
        )

        for task in done:
            # handle_message가 예상하지 못한 오류로 끝났다면 여기서 관찰한다.
            await task
```

실제 worker는 shutdown signal을 받으면 새 message claim을 중단하고, 진행 중인 작업을 제한 시간 안에 마치거나 checkpoint한 뒤 종료해야 한다. `MAX_IN_FLIGHT`도 단순 상수가 아니라 memory, downstream quota, job cost에 맞춰 조정해야 한다.

CPU-bound workload라면 같은 worker role을 다른 방식으로 구현할 수 있다.

```text
I/O worker process
   └─ asyncio event loop + bounded job concurrency

CPU worker pool
   └─ multiple processes, usually one task per allocated CPU slot

GPU inference worker
   └─ model server + batching + GPU memory ownership
```

즉 **worker는 역할이고 async/thread/process는 그 역할을 구현하는 도구**다.

## API와 worker의 책임을 분리하면 무엇이 달라지는가

| 책임 | API | Worker |
| --- | --- | --- |
| Authentication | 요청 identity 확인 | 검증된 identity context 사용 |
| Authorization | Run 생성 권한 확인 | Tool 실행 시 세부 policy 재검증 가능 |
| Request validation | 입력 schema와 제한 검사 | 실행 시 필요한 invariant 확인 |
| Run creation | `run_id`와 접수 상태 생성 | Attempt 생성과 running 전환 |
| Queue | 작업 제출 | 작업 claim, ack, retry |
| Agent execution | 짧은 동기 실행만 선택적으로 | 장시간 graph와 tool orchestration |
| Progress/event | 조회와 SSE 전달 | 상태 갱신과 event publish |
| Result | 조회 endpoint 제공 | 결과와 terminal failure 저장 |
| Scaling signal | Request rate, connection count | Queue depth, run latency, resource usage |

이 분리는 codebase를 반드시 두 repository로 나누라는 뜻이 아니다. 같은 domain model과 application package를 공유할 수 있다. 중요한 것은 process lifecycle과 scaling unit을 분리하는 것이다.

API는 짧고 예측 가능한 request handling에 최적화할 수 있다. Worker는 긴 timeout, tool credential, CPU/GPU resource, retry policy에 맞춰 따로 배포하고 scale할 수 있다. PDF parsing worker가 밀려도 status 조회 endpoint와 SSE connection까지 같이 고갈되지 않도록 failure domain도 분리된다.

## Worker가 자동으로 보장하지 않는 것

Worker를 추가하면 architecture diagram은 그럴듯해지지만 다음 성질이 저절로 생기지는 않는다.

| 필요한 성질 | 별도로 필요한 설계 |
| --- | --- |
| Process restart 이후 복구 | Durable queue와 redelivery |
| 중복 실행 안전성 | Idempotency key와 side-effect guard |
| 긴 run 재개 | Checkpoint와 resumable state |
| User cancellation | Durable cancellation protocol |
| Progress 조회 | External state/event storage |
| Poison message 격리 | Max attempts와 dead-letter policy |
| Overload 방지 | Admission control과 backpressure |
| 누가 실행 중인지 확인 | Lease, heartbeat 또는 pending ownership |

이것이 queue와 worker를 `create_task()`의 더 무거운 버전으로 보면 안 되는 이유다. Worker boundary는 recovery를 설계할 자리를 만들어주지만, recovery policy 자체는 아니다.

## Kubernetes에서 worker는 특별한 object가 아니다

Kubernetes에는 `Deployment`, `StatefulSet`, `Job` 같은 workload resource가 있다. 그러나 application architecture에서 말하는 worker는 Kubernetes object 이름이 아니다.

API와 worker가 같은 container image를 사용해도 된다.

```text
image: my-agent:1.0

API Deployment
  command: uvicorn app.api:app

Worker Deployment
  command: python -m app.worker
```

두 Deployment는 같은 code와 image를 공유하지만 서로 다른 command, replica count, resource request, autoscaling signal, secret scope를 가질 수 있다. Kubernetes Deployment는 application workload의 Pod 집합과 rollout을 관리하고, Pod는 영구적인 개체가 아니라 비교적 일시적인 실행 단위로 취급된다. ([Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/), [Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)) 따라서 진행 상태를 worker Pod의 memory에만 두면 Pod 교체와 함께 사라질 수 있다.

Kubernetes의 `Job`은 완료될 때까지 하나 이상의 Pod를 실행하는 별도 controller다. ([Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/)) Application의 모든 Agent run마다 Kubernetes Job을 만들어야 한다는 뜻은 아니다. 짧은 run이 많은 시스템은 장시간 실행되는 worker Deployment가 queue를 consume하는 편이 단순할 수 있고, 강한 resource isolation이 필요한 큰 batch workload는 Kubernetes Job이 맞을 수 있다. 선택은 workload granularity와 startup cost, isolation 요구에 달려 있다.

Kubernetes 배포와 autoscaling은 Article 11에서 더 자세히 다룬다. 지금 필요한 mental model은 하나다.

> Container가 worker인 것이 아니다. Queue에서 받은 execution attempt를 책임지는 application role이 worker다.

## Request에서 worker로 ownership을 넘기는 판단 기준

최종적으로는 다음 질문으로 결정할 수 있다.

1. Client connection이 끊겨도 실행을 계속해야 하는가?
2. API deploy나 crash 뒤에도 작업을 다시 찾아야 하는가?
3. Retry, cancellation, progress, audit가 필요한가?
4. API와 다른 resource profile이나 scaling policy가 필요한가?
5. 같은 run이 다시 전달될 때 안전하게 처리할 수 있어야 하는가?

대부분 `아니오`이고 작업이 짧다면 request handler가 직접 `await`하는 구조가 가장 단순하다. 일부만 `예`여도 queue와 worker boundary를 검토할 이유가 생긴다. Architecture는 component 수가 아니라 필요한 failure semantics에 의해 커져야 한다.

Worker를 도입하면 Agent run의 owner는 명확해진다. 하지만 다음 문제가 곧바로 나타난다.

- Worker가 실행 중인 현재 state는 어디에 저장하는가?
- API는 progress를 어떻게 읽는가?
- Worker가 죽은 뒤 새 worker는 어디에서 이어가는가?
- 최종 결과와 임시 scratch state를 같은 storage에 넣어도 되는가?
