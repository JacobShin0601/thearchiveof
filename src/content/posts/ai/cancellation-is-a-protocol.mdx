앞선 글 [Agent Request 하나를 끝까지 따라가 보기](/ai/agents/agent-request-end-to-end/)에서는 API가 run을 만들고, Queue가 전달하며, Worker가 실행하고, PostgreSQL result commit 뒤 `XACK`하는 전체 경로를 연결했다.

이제 사용자가 실행 도중 Cancel을 누른다. 가장 단순한 endpoint는 이렇게 보일 수 있다.

```python
@app.post("/runs/{run_id}/cancel")
async def cancel_run(run_id: UUID):
    await db.execute(
        "UPDATE runs SET status = 'cancelled' WHERE run_id = $1",
        run_id,
    )
```

응답은 즉시 성공하지만 Worker는 계속 tool을 호출하고, 외부 API는 결제를 끝내며, 잠시 뒤 결과가 `succeeded`로 덮어쓸 수 있다. 화면의 상태값만 취소됐을 뿐 실행은 취소되지 않았다.

Cancellation은 한 번의 write가 아니다. **의도를 durable하게 접수하고, 실행 주체에 전파하고, 안전 경계에서 멈추고, 마지막 상태 경쟁을 해결하는 protocol**이다.

## `cancel_requested`와 `cancelled`는 다른 사실이다

두 상태는 서로 다른 질문에 답한다.

| 기록 | 의미 |
| --- | --- |
| `cancel_requested_at` | 사용자의 중단 의도를 시스템이 durable하게 받았는가? |
| `status = cancelling` | 실행 주체가 중단 절차를 진행 중인가? |
| `status = cancelled` | 실행과 cleanup이 끝나 terminal 결과를 확정했는가? |

취소 API는 tenant와 run ownership을 검증하고, active 상태에서만 조건부 update한다.

```sql
UPDATE runs
SET cancel_requested_at = COALESCE(cancel_requested_at, now()),
    cancel_requested_by = COALESCE(cancel_requested_by, $3),
    status = 'cancelling'
WHERE run_id = $1
  AND tenant_id = $2
  AND status IN ('queued', 'running')
RETURNING run_id, status, cancel_requested_at;
```

`RETURNING` 결과가 있다면 요청이 접수됐다. 결과가 없다면 row를 다시 읽어 이미 `cancelling` 또는 `cancelled`인지, 완료가 먼저 승리했는지, 접근 권한이 없는지 구분한다. 같은 요청을 여러 번 보내도 같은 결과를 반환하는 멱등 endpoint가 되어야 한다.

```http
POST /runs/7d5.../cancel

HTTP/1.1 202 Accepted
{
  "run_id": "7d5...",
  "status": "cancelling",
  "cancel_requested_at": "2026-10-12T08:15:30Z"
}
```

`202`는 취소 완료가 아니라 **취소 요청을 안전하게 접수했다**는 뜻이다.

## PostgreSQL은 진실이고 Redis는 빠른 신호다

DB만 주기적으로 확인하면 durable하지만 반응이 느리다. Redis flag나 Pub/Sub만 사용하면 빠르지만 expiry, restart, message loss 뒤에 취소 의도가 사라질 수 있다. 두 역할을 나눈다.

```python
run = await run_store.request_cancel(
    tenant_id=identity.tenant_id,
    run_id=run_id,
    requested_by=identity.user_id,
)

await redis.set(f"run:{run_id}:cancel", "1", ex=86_400)
await redis.publish("agent:cancellations", str(run_id))
```

- PostgreSQL의 `cancel_requested_at`은 재시작과 queue redelivery 뒤에도 남는 판단 기준이다.
- Redis flag는 active Worker가 step 사이에서 빠르게 확인하는 cache다.
- Pub/Sub는 오래 기다리는 Worker를 깨우는 힌트다. 전달 보장은 맡기지 않는다.

Redis 쓰기가 실패해도 취소 요청 자체는 성공이다. Worker는 durable row를 다시 읽어 결국 중단할 수 있어야 한다. 반대로 Redis 신호만 보고 PostgreSQL에 기록이 없다면 terminal 전환 전에 durable truth를 재확인한다.

## Worker는 안전 경계에서 협력적으로 멈춘다

Worker는 긴 함수 마지막에 한 번만 확인해서는 안 된다. Queue claim 직후, graph node 전후, remote call 전후, retry 직전에 cancellation checkpoint를 둔다.

```python
class RunContext:
    async def raise_if_cancel_requested(self) -> None:
        cached = await redis.exists(f"run:{self.run_id}:cancel")
        if cached or await run_store.is_cancel_requested(self.run_id):
            raise asyncio.CancelledError

async def run_step(ctx: RunContext):
    await ctx.raise_if_cancel_requested()

    result = await call_tool()

    await ctx.raise_if_cancel_requested()
    return result
```

Checkpoint를 너무 촘촘히 두면 store 부하가 커지고, 너무 성기면 Cancel 버튼이 늦게 반응한다. 외부 호출처럼 오래 걸리거나 부수 효과가 생기는 경계가 우선이다. CPU-bound 작업은 async checkpoint에 도달하지 않으므로 작은 chunk로 나누거나 별도 process에 실행하고 제어 채널을 둬야 한다.

Queue에만 있고 아직 실행되지 않은 run도 같은 protocol을 따른다. Worker가 entry를 받으면 durable run부터 읽는다.

```python
run = await run_store.get(run_id)

if run.cancel_requested_at is not None:
    await run_store.mark_cancelled_before_start(run_id, entry_id)
    await append_event(run_id, "run_cancelled")
    await queue.ack(entry_id)
    return
```

Worker가 죽어 entry가 reclaim되어도 새 Worker가 같은 기록을 보고 실행하지 않는다.

## `Task.cancel()`은 요청이지 kill switch가 아니다

Python의 `asyncio.Task.cancel()`은 task를 강제로 제거하지 않는다. 다음 실행 기회에 `CancelledError`가 발생하도록 요청한다. Coroutine이 예외를 삼키거나 await 지점에 도달하지 않으면 중단이 지연되거나 무시될 수 있다.

```python
async def execute_run(ctx: RunContext):
    try:
        return await graph.ainvoke(ctx.input, config=ctx.config)
    except asyncio.CancelledError:
        await append_event(ctx.run_id, "worker_cancellation_observed")
        raise
    finally:
        await ctx.close_open_resources()
```

`CancelledError`는 일반적인 업무 실패가 아니다. cleanup을 위해 잡았다면 특별한 이유가 없는 한 다시 raise해야 한다. 삼키면 structured concurrency가 child task 종료를 기다리며 꼬이거나 상위 계층이 성공처럼 처리할 수 있다.

```python
async with asyncio.TaskGroup() as group:
    search = group.create_task(search_sources(ctx))
    extract = group.create_task(extract_documents(ctx))
```

Parent run이 취소되면 child task도 중단 신호를 받아야 한다. 그러나 메모리의 task handle만으로는 Worker restart를 견딜 수 없다. child가 공통 `run_id`의 durable flag를 확인하고, local task cancellation은 반응 속도를 높이는 수단으로 사용한다.

## Local task를 멈춰도 remote work는 계속될 수 있다

LLM 요청, 브라우저 자동화, 데이터 warehouse query를 기다리는 coroutine을 취소해도 원격 서버가 실제 계산을 중단했다는 뜻은 아니다.

<AgentCancellationDiagrams
  kind="boundaries"
  language="ko"
  caption="그림 3. Local coroutine, remote operation, 이미 commit된 side effect는 서로 다른 취소 계약을 가진다."

Provider가 비동기 operation ID와 cancel API를 제공한다면 ID를 먼저 저장한다.

```python
operation = await provider.start(request, idempotency_key=tool_call_id)
await tool_store.attach_remote_operation(
    tool_call_id=tool_call_id,
    operation_id=operation.id,
)

try:
    return await provider.wait(operation.id)
except asyncio.CancelledError:
    await provider.cancel(operation.id)
    raise
```

Cancel API가 없거나 이미 늦었다면 Worker가 할 수 있는 것은 **기다리기를 중단하고 늦게 온 결과를 채택하지 않는 것**이다. 이때 attempt fence가 필요하다.

```sql
UPDATE tool_calls
SET status = 'succeeded', output_json = $4
WHERE tool_call_id = $1
  AND attempt_id = $2
  AND fence = $3
  AND status = 'running';
```

취소가 fence를 폐기한 뒤라면 늦은 Worker의 update는 0 row다. 네트워크 호출 자체를 멈추지 못해도 stale result가 product state로 들어오는 것은 막을 수 있다.

## 이미 발생한 부수 효과는 취소가 아니라 보상 문제다

메일을 보냈고, 티켓을 만들었고, 결제가 승인된 뒤 Cancel이 도착할 수 있다. Python stack을 되감아도 외부 세계는 되돌아가지 않는다.

Tool step은 실행 전에 성격을 분류해야 한다.

| 종류 | 예 | Cancellation 정책 |
| --- | --- | --- |
| 읽기 | 검색, 문서 조회 | 대기 중단, 늦은 결과 폐기 |
| 멱등 쓰기 | 동일 key의 draft 저장 | 같은 idempotency key로 재시도 가능 |
| 보상 가능한 쓰기 | 임시 예약 | 취소 후 별도 release/void command |
| 비가역 쓰기 | 발송, 외부 게시 | 실행 전 승인, 실행 후 감사 event |

보상 작업은 transaction rollback이 아니라 새로운 업무 명령이다. 실패할 수도 있고 권한이 추가로 필요할 수도 있으므로 원래 실행의 `cancelled`와 보상의 `pending/succeeded/failed`를 따로 기록한다.

## 완료와 취소가 동시에 도착하면 하나만 terminal이 된다

Worker가 결과를 저장하는 순간 Cancel 요청이 들어올 수 있다. 애플리케이션 코드에서 먼저 읽고 나중에 쓰면 둘 다 자신이 이겼다고 판단한다. terminal update 자체를 조건부로 만든다.

<AgentCancellationDiagrams
  kind="race"
  language="ko"
  caption="그림 4. 완료와 취소는 같은 active 상태 집합을 조건부로 갱신하며, 먼저 commit한 terminal 결과만 유효하다."
/>

```sql
UPDATE runs
SET status = 'cancelled',
    cancelled_at = now(),
    terminal_attempt_id = $2
WHERE run_id = $1
  AND status IN ('queued', 'running', 'cancelling')
  AND active_fence = $3
RETURNING *;
```

완료 path도 같은 active 상태 집합과 fence를 사용한다. 먼저 commit한 쪽이 terminal slot을 얻고, 나중 update는 0 row가 된다. “Cancel을 눌렀으니 무조건 cancelled”가 아니라 제품 정책을 명시해야 한다. 이 글의 권장 기본값은 다음과 같다.

- 결과가 먼저 durable하게 commit됐다면 `succeeded`를 유지하고 `cancellation_arrived_too_late` event를 남긴다.
- 취소가 먼저 terminal commit됐다면 늦은 result write를 fence로 거부한다.
- 부수 효과는 성공했지만 결과 commit 전 취소됐다면 execution ledger와 compensation 상태를 함께 보여준다.

## SSE 연결 종료는 취소 명령이 아니다

사용자가 탭을 닫거나 이동 통신이 끊겨 SSE connection이 종료될 수 있다. 이것을 run cancellation으로 해석하면 잠깐의 네트워크 장애가 업무 중단으로 바뀐다.

```text
SSE disconnect  → 관측 channel 종료 → run 계속
POST /cancel    → durable intent 기록 → cancellation protocol 시작
```

UI는 `cancellation_requested`, `step_cancelling`, `run_cancelled`처럼 진행을 보여주는 event를 받을 수 있다. 재연결하면 durable run과 event cursor로 상태를 복원한다.

## `XACK`은 취소 terminal commit 뒤에 한다

실행 성공과 마찬가지로 취소도 queue acknowledgement보다 durable terminal record가 먼저다.

```python
try:
    result = await execute_run(ctx)
except asyncio.CancelledError:
    won = await run_store.commit_cancelled(
        run_id=run.id,
        attempt_id=attempt.id,
        fence=attempt.fence,
    )
    if won:
        await append_event(run.id, "run_cancelled")
finally:
    if await run_store.is_terminal(run.id):
        await queue.ack(entry_id)
```

`XACK` 뒤 terminal commit 전에 Worker가 죽으면 queue는 작업을 잊는데 run은 계속 `cancelling`으로 남는다. 반대로 terminal commit 뒤 `XACK` 전에 죽으면 entry가 재전달되지만 새 Worker가 terminal row를 확인하고 실행 없이 ack할 수 있다.

## Cancellation 테스트는 타이밍을 흔들어야 한다

Happy path 하나로는 race를 찾기 어렵다. 최소한 다음 지점을 제어해 테스트한다.

- Queue 대기 중 취소: Worker가 tool을 한 번도 호출하지 않는가?
- 첫 tool 직전 취소: checkpoint가 실행을 막는가?
- Remote call 대기 중 취소: cancel API를 호출하거나 늦은 결과를 거부하는가?
- 비가역 side effect 직후 취소: ledger와 compensation 상태가 정확한가?
- 결과 commit과 취소의 동시 경쟁: terminal status가 하나뿐인가?
- `cancelling` 중 Worker crash: reclaim한 Worker가 실행을 재개하지 않는가?
- 같은 Cancel 반복: 동일한 결과를 반환하는가?
- SSE disconnect: run이 계속 실행되는가?

```python
async def test_cancel_wins_terminal_race(run_store, worker):
    gate = Barrier(2)

    complete = worker.complete_after(gate)
    cancel = run_store.cancel_after(gate)
    await asyncio.gather(complete, cancel)

    run = await run_store.get("R1")
    assert run.status in {"succeeded", "cancelled"}
    assert await run_store.terminal_transition_count("R1") == 1
```

중요한 assertion은 특정 coroutine이 예외를 받았다는 사실이 아니다. **더 이상 유효한 write가 발생하지 않고, terminal truth가 하나이며, queue가 결국 정리되는가**다.

## 구현 체크리스트

- Cancel endpoint가 tenant와 run ownership을 확인하는가?
- `cancel_requested_at`이 Redis가 아닌 durable store에 남는가?
- 요청 접수와 실제 종료를 `cancelling`과 `cancelled`로 구분하는가?
- Queue claim, node, remote call, retry 경계에 checkpoint가 있는가?
- `CancelledError` cleanup 뒤 다시 raise하는가?
- Parent와 child task가 durable cancellation context를 공유하는가?
- Remote operation ID와 provider cancel contract를 저장하는가?
- 늦은 result write를 attempt fence로 거부하는가?
- 비가역 side effect 전 approval과 idempotency policy가 있는가?
- 완료와 취소가 조건부 terminal update 하나를 경쟁하는가?
- SSE disconnect와 explicit Cancel을 구분하는가?
- Terminal commit 뒤에 cancellation event와 `XACK`을 수행하는가?

## 취소 다음에는 시간의 경계를 설계해야 한다

Cancellation은 사용자가 “그만”이라고 말하는 명시적 의도다. 하지만 사용자가 버튼을 누르지 않아도 LLM 호출이 무한히 기다리거나, 전체 run이 비용 한도를 넘거나, deadline 이후 결과가 무의미해질 수 있다.

다음 글에서는 **Timeout, Deadline, Budget은 서로 같은 숫자가 아니다**라는 관점에서 각 hop의 timeout, end-to-end deadline, retry budget과 비용 budget을 하나의 실행 정책으로 연결한다.
