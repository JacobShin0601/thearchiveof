## 1. 요청을 받아 기록한다

### API의 첫 책임은 실행이 아니라 검증이다

브라우저는 대화 session 아래에 새 run을 요청한다. API는 이 시점에 LLM이나 tool을 실행하지 않는다. 먼저 인증된 사용자와 session의 소유 관계, 그리고 업무 입력만 확인한다.

```python
@app.post("/sessions/{session_id}/runs", status_code=202)
async def create_run(
    session_id: UUID,
    request: AnalysisRequest,
    identity: Annotated[Identity, Depends(current_identity)],
):
    session = await load_owned_session(
        tenant_id=identity.tenant_id,
        user_id=identity.user_id,
        session_id=session_id,
    )
    if session is None:
        raise HTTPException(404, "session not found")
```

SSO나 ingress가 인증을 마쳤더라도, 클라이언트가 보낸 `X-User-ID` 같은 임의 header를 그대로 믿으면 안 된다. 여기까지 통과한 뒤에야 Redis key, checkpoint, 실행 기록에 접근할 수 있다.

### 202를 돌려주기 전에 남겨야 할 것

API process가 응답 직후 죽어도 요청을 다시 발견하려면, `run_id`와 입력이 process 밖에 남아 있어야 한다. 이 글의 기준 구현은 **run row와 outbox row를 같은 PostgreSQL transaction에 기록하는 방식**이다.

```sql
BEGIN;

INSERT INTO runs (run_id, tenant_id, user_id, session_id, status, input_json)
VALUES (:run_id, :tenant_id, :user_id, :session_id, 'submitting', :input_json);

INSERT INTO run_outbox (event_id, run_id, topic, payload_json)
VALUES (:event_id, :run_id, 'agent:jobs', :payload_json);

COMMIT;
```

`submitting`은 “사용자 요청은 안전하게 받았지만, 아직 Queue 전달이 끝났는지는 확인하지 못했다”는 뜻이다. `queued`라고 바로 기록하면 DB row만 생기고 Queue 전달이 실패한 경우를 표현하기 어렵다.

간단한 시스템이라면 DB 기록 뒤 `XADD`를 바로 호출하고, `submitting` run을 주기적으로 다시 게시하는 reconciler를 둘 수 있다. 다만 둘 중 무엇을 쓰든 원칙은 같다. **202 Accepted는 Queue가 이미 실행했다는 뜻이 아니라, 요청을 복구 가능한 형태로 받았다는 뜻**이다.

## 2. 실행권을 넘긴다

run과 outbox가 남은 뒤 relay가 Redis Stream에 작은 실행 메시지를 게시한다. 큰 prompt나 대화 전체를 복제하지 않고, Worker가 durable store에서 다시 읽을 식별자만 보낸다.

```python
await redis.xadd(
    "agent:jobs",
    {
        "run_id": str(run_id),
        "session_id": str(session_id),
        "outbox_event_id": str(event_id),
    },
)
```

relay가 Redis 게시 뒤 완료 표시 전에 죽으면 같은 메시지가 다시 게시될 수 있다. 그래서 outbox는 exactly-once를 약속하는 장치가 아니다. **중복 delivery를 허용하되, Worker가 같은 run을 다시 실행하지 않게 만드는 장치**다.

### Queue entry와 Worker attempt는 다르다

Worker replica 중 하나가 consumer group에서 entry를 읽으면, 그 entry는 PEL에 남는다. 하지만 Worker는 payload만 믿고 tool을 호출하지 않는다. PostgreSQL에서 run을 다시 읽어 이미 끝났는지, 취소됐는지, 이번 attempt가 실행 권한을 갖는지 확인한다.

```python
run = await run_store.get(run_id)

if run.status in {"succeeded", "failed", "cancelled"}:
    await queue.ack(entry_id)
    return

attempt = await run_store.start_attempt(
    run_id=run.id,
    worker_id=worker_id,
)
```

`attempt_id`와 fencing token은 “이번 delivery가 가진 실행 권한”을 구분한다. Worker가 죽고 다른 Worker가 reclaim하면 같은 run 아래 새 attempt가 생길 수 있다. 이때 이전 Worker의 늦은 결과가 최종 결과를 덮지 못하게, terminal update는 attempt와 fence를 조건으로 원자적으로 처리해야 한다.

## 3. 실행 결과를 화면용으로 번역한다

### Session, run, attempt는 같은 ID가 아니다

Worker는 실행 전에 서로 다른 목적의 정보를 읽는다.

- **session**: 이전 대화와 지속되는 context
- **run**: 사용자가 이번에 요청한 실행
- **attempt**: 특정 Worker가 수행하는 한 번의 시도
- **checkpoint**: LangGraph가 재개를 위해 보관하는 runtime 상태

LangGraph의 `thread_id`는 session context를 잇는 runtime key가 될 수 있지만, 이번 요청의 `run_id`와 같지 않다. 이 구분이 있어야 “대화는 이어지지만, 이전 실행의 실패를 다음 실행으로 넘기지 않는다”는 원칙을 지킬 수 있다.

### 그래프 내부 상태를 그대로 브라우저에 보내지 않는다

`graph.astream()`에서 나오는 값은 그래프를 실행하기 위한 내부 값이다. 브라우저가 필요한 것은 그 전체가 아니라, 현재 화면을 복원할 작은 state와 시간순으로 보여 줄 event다.

```python
async for part in graph.astream(
    build_graph_input(run),
    config=config,
    stream_mode=["updates", "custom"],
    version="v2",
):
    await project_stream_part(run, attempt, part)
```

`updates`는 화면용 현재 상태로 줄여 Redis Hash에 저장하고, `custom`은 진행 상황·승인 요청처럼 남겨야 할 사건으로 정규화해 Redis Stream에 append한다. 실제 event 형식은 사용 중인 LangGraph 버전에 맞춰 한 곳에서 변환하는 편이 안전하다.

### 브라우저는 실행자가 아니라 관측자다

브라우저는 202을 받으면 먼저 run의 현재 상태, 최근 event, 이어 읽을 cursor를 가져온다. 그다음 SSE를 연결한다. 처음부터 SSE만 기다리면 연결 전에 생긴 상태를 놓칠 수 있다.

연결이 끊겨도 Worker run은 계속된다. 재연결한 브라우저는 마지막으로 적용한 `event_id` 이후를 다시 받고, event 보존 기간을 넘겼다면 snapshot을 다시 읽는다. SSE endpoint도 session·run 소유권을 확인해야 한다. streaming 연결이라고 해서 권한 검사가 사라지는 것은 아니다.

## 4. 완료를 확정한다

Graph가 결과를 냈다고 Queue 작업까지 끝난 것은 아니다. 완료에는 순서가 있다.

1. final result와 terminal status를 PostgreSQL에 확정한다.
2. Redis의 화면용 state를 completed로 갱신한다.
3. completion event를 append한다.
4. 마지막에 Queue entry를 `XACK` 한다.

```python
result = await execute_graph(run, attempt)

await run_store.complete(
    run_id=run.id,
    attempt_id=attempt.id,
    fence=attempt.fence,
    result=result,
)

await redis.hset(f"run:{run.id}:state", mapping={"status": "succeeded"})
await append_completion_event(run.id)
await redis.xack("agent:jobs", "agent-workers", entry_id)
```

Redis projection이나 completion event 기록이 실패해도 PostgreSQL의 terminal row가 최종 기준이다. 반대로 result commit 뒤 XACK 전에 Worker가 죽으면 entry는 다시 전달된다. 새 Worker는 terminal status를 확인하고 graph를 다시 실행하지 않은 채 XACK만 한다.

이 순서가 중요한 이유는 간단하다. **ack는 “다시는 이 일을 볼 필요가 없다”는 신호이므로, 그 전에 결과가 안전하게 남아 있어야 한다.**

## 5. 장애 뒤에도 다시 찾는다

정상 경로만 따라가면 설계가 그럴듯해 보인다. 실제로는 각 경계에서 process가 멈췄을 때 무엇이 남는지가 더 중요하다.

### 운영 로그는 연결된 ID를 남겨야 한다

`run_id` 하나만으로는 부족하다.

- `session_id`: 어떤 지속 대화에 속하는가
- `run_id`: 사용자가 요청한 실행은 무엇인가
- `attempt_id`: 어떤 Worker 시도가 수행했는가
- `queue_entry_id`: 어떤 delivery가 pending 또는 ack 되었는가
- `event_id`: 브라우저가 어디까지 관측했는가
- `tool_call_id`: 외부 부수 효과를 중복 없이 식별하는가

이 연결이 있어야 “사용자는 결과를 못 봤는데 tool은 실행됐는가?” 같은 운영 질문에 답할 수 있다.

### 테스트도 경계 전체를 끊어 봐야 한다

최소 happy path는 실제 API, Queue, Worker, store를 연결한다. 하지만 더 중요한 것은 각 경계에서 멈추게 하는 테스트다.

- run commit 뒤, Queue publish 전
- `XREADGROUP` 뒤, attempt 생성 전
- tool side effect 뒤, execution ledger commit 전
- result commit 뒤, `XACK` 전
- SSE event 수신 뒤, UI 적용 전

각 테스트의 assertion은 “에러가 발생했다”가 아니다. **run이 유실되지 않고, 부수 효과가 중복되지 않으며, 사용자가 결국 최종 결과를 다시 읽을 수 있는가**여야 한다.

## 이 설계에서 섞으면 안 되는 네 가지

- session과 run
- Queue delivery와 Worker attempt
- LangGraph 내부 state와 화면용 state
- 결과 확정과 Queue ack

하나의 요청을 끝까지 따라가면 경계가 선명해진다. 다음 질문도 자연스럽게 나온다. 사용자가 실행 중 취소를 누르면 누가 멈추고, 이미 시작한 tool은 어떻게 다뤄야 할까?

다음 글에서는 **Cancellation은 state값이 아니라 protocol**이라는 관점에서, 취소 요청·Worker의 cooperative check·tool boundary·terminal state 경쟁을 다룬다.
