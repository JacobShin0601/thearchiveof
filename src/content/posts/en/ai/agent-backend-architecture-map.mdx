The previous article, [Agent Pattern Design](/en/ai/agents/agent-pattern-design/), treated an agent as a composition of bounded control flows: tool use, parallelism, planning, HITL, retry, and reflection. Patterns answer **what happens inside a run**.

Production immediately adds different questions:

- Should a 30-second or three-minute run stay inside an HTTP handler?
- When the user closes a tab, should execution stop?
- Where do progress and checkpoints live, and what do we stream to the browser?
- If an API Pod restarts, how do we rediscover in-flight runs?

This article is the **one-page map** for those questions. Later articles go deep in Python; here we align components and ownership first.

## 1. After patterns, you need a backend map

Demos often start a run with one line:

```python
asyncio.create_task(run_agent(request))
return {"status": "started"}
```

From a pattern perspective, a tool loop is running. From a backend perspective, **who issued the run_id, where do clients poll after failure, and does work survive deploy** are still undefined.

## 2. One map: command flow and observation flow

In the figure below, **solid** arrows are how the user **commands** execution. **Dashed** arrows are how the browser **observes** progress. The design starts by refusing to merge both into one long HTTP call.

<AgentBackendArchitectureMap kind="overview" language="en" />

```text
Command:     Browser ──POST──> API ──publish──> Queue ──claim──> Worker
Observation: Browser <──SSE── API <──read──── Redis / PostgreSQL <──write── Worker
```

The worker runs LLM calls, tools, and checkpoints. The API mostly creates runs, publishes to the queue, serves reads, and relays SSE. That split lets API and worker replica counts track **different resource profiles**.

### Four boundaries to read in the diagram

The map has many boxes, but only four handoff contracts matter:

| Boundary | What crosses it | What does not | Failure response |
| --- | --- | --- | --- |
| Browser → API | User intent, idempotency key | Execution lifetime | Detect duplicate submissions |
| API → Queue | `run_id`, minimal execution payload | User HTTP connection | Outbox relay retries publish |
| Queue → Worker | Claim, lease, `attempt_id` | Exactly-once guarantee | Another worker reclaims after lease expiry |
| Worker → Stores | Versioned snapshot, events, result | Process memory | Resume and reconcile from durable state |

**PostgreSQL and Redis are not interchangeable “state stores.”** PostgreSQL is the record that must explain a run after restart. Redis is a bounded projection layer for active coordination and delivery. SSE is not a store at all; it transports snapshots and events that already exist elsewhere.

The edge from a worker to an external LLM or tool is also different from an internal state transition. It needs timeouts and retries, plus an explicit idempotency contract for side effects such as creating a ticket or charging an account.

## 3. Pod, process, worker, thread — not the same axis

When Kubernetes, Python, and agent vocabulary land in one sentence, designs wobble.

| Term | What it denotes | Agent backend example |
| --- | --- | --- |
| **Pod** | Schedulable, restartable unit ([Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)) | One Pod in the API Deployment, one in the worker Deployment |
| **Process** | OS-isolated running program | Uvicorn worker process inside a Pod |
| **Worker (role)** | Service that claims queue jobs and owns a run attempt | `agent-worker` Deployment |
| **Thread / async task** | In-process concurrency **tool** | Thread pool for a blocking SDK |

When a Pod restarts, its processes and asyncio tasks go with it. The **worker role** is designed so queue messages and PostgreSQL runs let another Pod resume. A “thread pool worker” is parallel hardware inside one process—not the same thing as a queue consumer.

## 4. The API does not own execution — `202 Accepted`

Starting a long run usually follows this contract:

1. Validate and authorize
2. Insert a run row in PostgreSQL (`submitting` or `queued`)
3. Publish an execution message to the queue
4. Return **`202 Accepted`** and `run_id`

```python
@app.post("/runs", status_code=202)
async def create_run(request: RunRequest, user: User = Depends(current_user)):
    authorize(user, request)
    run_id = new_run_id()
    await run_store.create(run_id=run_id, user_id=user.id, status="submitting", input=request)
    await job_queue.publish({"run_id": run_id, "input": request.model_dump()})
    await run_store.mark_queued(run_id)
    return {"run_id": run_id, "status": "queued"}
```

`202` means the request was accepted and processing continues asynchronously—not that the browser connection guarantees survival. Queues, workers, and durable state provide that.

FastAPI [Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/) suit short post-response work; the same docs steer heavy work toward queues. Agent runs usually belong in the second bucket.

## 5. HTTP disconnect vs the worker

Closing a tab or dropping SSE removes the **observation path** only. A run already accepted on the command path typically keeps going.

```text
POST /runs              → 202 + run_id   (handler returns)
GET /runs/{id}/events   → SSE            (disconnect stops chunks; worker continues)
```

An SSE handler may watch `request.is_disconnected()` and signal cancellation—that is product policy. The default assumption is **run lifetime ≠ HTTP connection lifetime**. Progress and checkpoints live in Redis and PostgreSQL; the browser catches up with `Last-Event-ID`.

The asyncio task inside a worker does not share lifecycle with the API handler that once streamed events. Cancelling the stream does not stop the queue consumer in another Pod.

## 6. The queue is not exactly-once

Brokers usually offer **at-least-once delivery**, not exactly-once execution.

- If a consumer dies before ack, the message reappears
- After lease expiry, another worker may claim the same job
- Retries can publish twice

Agent steps may call LLMs, external APIs, or create tickets—**side effects**. Workers must decide “is this the first processing of this message?” via `attempt_id`, lease, or idempotency keys. Do not expect the queue to dedupe; design **idempotent steps and explicit duplicate detection**.

| Guarantee | Meaning | Typical agent response |
| --- | --- | --- |
| At-most-once | Loss possible, no duplicates | Rare for important runs |
| At-least-once | Duplicates possible, low loss | Default with queue + worker |
| Effectively-once | Looks once to users | Idempotent effects + dedup |

## 7. Transactional outbox — tie acceptance to publish

Separate `run_store.create` and `job_queue.publish` calls leave gaps: a row without a message, or a message without a row, if the process dies between them.

Production often uses a **transactional outbox**:

```text
BEGIN;
  INSERT INTO agent_runs (...);
  INSERT INTO outbox (topic, payload) VALUES ('run.execute', ...);
COMMIT;
──> relay process reads outbox and publishes to the queue
```

Committing run and outbox together means a dead API process still leaves recoverable intent for a relay. Alternatives make the queue authoritative and lean harder on consumer idempotency. Either way, before `202` the system must leave **execution intent you can rediscover later**.

## 8. PostgreSQL and Redis — what goes where

Do not put every kind of state in one store.

| Store | Good fit | Why |
| --- | --- | --- |
| **PostgreSQL** | Run metadata, final status, JSON/JSONB input and results, checkpoint snapshots, audit | ACID, reporting, retention ([JSON types](https://www.postgresql.org/docs/current/datatype-json.html)) |
| **PostgreSQL + pgvector** | Embeddings, RAG context | Tool retrieval colocated with lifecycle data ([pgvector](https://github.com/pgvector/pgvector)) |
| **Redis Hash** | Current progress, heartbeat, `last_event_id` | Frequent updates, TTL, UI snapshot |
| **Redis Stream** | Bounded delivery events, SSE replay cursor ([Streams](https://redis.io/docs/latest/develop/data-types/streams/)) | Short reconnect window for observation |

Workers commit checkpoints to PostgreSQL and use atomic Lua for Hash + Stream on UI transitions. PostgreSQL answers “did this run ultimately succeed?” Redis answers “what should the UI show right now?” Bound Stream length and retention; send long-term event history and audit records to PostgreSQL or a separate log system.

## 9. `updated_at` alone does not fix concurrency

Two workers updating the same run can let **late stale progress** overwrite fresh state. Comparing only `updated_at` does not prove a write belongs to the current attempt.

Safer patterns:

- Monotonic **version** or sequence
- **Fencing token** with queue **lease** — reject writes from a worker whose lease expired
- Single writer — one attempt owns hot-path updates

```python
async def update_progress(run_id: str, attempt_id: str, version: int, progress: int) -> bool:
    return await run_store.update_if_match(
        run_id,
        attempt_id=attempt_id,
        expected_version=version,
        progress=progress,
    )
```

Redis snapshots with only `updated_at` suffer the same race: a late heartbeat from an old attempt can rewind the bar. [Where Agent State Lives](/en/ai/agents/where-agent-state-lives/) goes deeper on version and fencing.

## 10. SSE, replay, and idempotency

The observation path sends `id`, `event`, and `data` per the [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html) format. Clients reconnect with `Last-Event-ID`; servers resume with `XREAD` from the Redis Stream cursor.

Think about idempotency at two layers:

1. **Transport** — delivering the same Stream entry twice after reconnect should be harmless (`event_id` dedup in the UI)
2. **Domain** — publishing the same transition twice should not flip snapshot twice (Lua atomicity, version checks)

```text
id: 1696400000000-0
event: progress
data: {"progress": 65, "step": "dcf"}
```

When a generator sees disconnect, it stops HTTP chunks only. Events already appended remain for the next SSE session. **A broken stream is not a run rollback**.

## 11. Dev vs prod: why split Deployments

Locally, API and worker in one process or Pod is fine for learning. In production, split [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

<AgentBackendArchitectureMap kind="deployment" language="en" />

| Environment | Shape | Benefit |
| --- | --- | --- |
| Dev | Single process or Pod | Simple debugging |
| Prod | `agent-api` + `agent-worker` Deployments | Independent scale and rolling updates |

Scale API replicas for short HTTP latency; scale workers for GPU, memory, and concurrent runs. Pair graceful shutdown (`SIGTERM`, finish or release leases) with [Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) behavior.

## 12. One run through the system

The lifecycle figure shows how command and observation interleave over time.

<AgentBackendArchitectureMap kind="lifecycle" language="en" />

```text
1. POST /runs
2. PostgreSQL run row (submitting → queued)
3. outbox / queue publish
4. 202 + run_id
5. worker claim → running
6. checkpoint / progress / stream events
7. completed or failed (PostgreSQL commit)
8. GET /runs/{id}, SSE replay for observation
```

### Failure paths matter as much as the happy path

Each numbered step needs a recovery source:

| Failure point | Information that must remain | Next action |
| --- | --- | --- |
| API exits after run creation | `agent_runs` + outbox row | Relay publishes to queue |
| Worker exits after claim | Queue lease + `attempt_id` | A new attempt reclaims after expiry |
| Tool finishes but checkpoint fails | Non-terminal run state | Do not ack; retry idempotently |
| Redis eviction or TTL expiry | PostgreSQL snapshot and result | Reload snapshot and reset stream cursor |
| SSE disconnects | Bounded recent Stream events or PostgreSQL snapshot | Reconnect and replay, or resync |

Termination order is part of the contract. A worker does not ack a queue message before committing an important result to PostgreSQL. Conversely, a failed Redis progress write should not roll back a completed business result. Rebuild the Redis projection from PostgreSQL instead.

Tool loops, HITL, and retry from pattern design run in steps 5–6 **inside the worker**. This map fixes **which infrastructure owns the lifecycle** around that loop.
