<AnswerBlock question="Why does vLLM need tuning at all?">
  Allocating a GPU and loading a model is only the beginning. Even with the same model on the same hardware, latency and throughput can change substantially depending on how many sequences run concurrently, how tokens are budgeted per scheduling step, and how much memory is available for KV cache. Tuning vLLM is therefore less about maximizing GPU utilization and more about finding a stable operating point that meets TTFT and TPOT targets while maximizing sustainable throughput.
</AnswerBlock>

## 1. The engineering starts after the model loads

I work with on-premises AI in a large Korean enterprise. Security requirements around nationally designated core technologies mean that sending every request to an external commercial API is not an option. We serve open-source models through vLLM in Kubernetes Pods, with internal applications and agents sharing the inference service. This article describes the engineering decisions involved, without disclosing an organization's infrastructure or operating data.

A model that loads successfully and returns a response is a useful milestone. It is not yet a capacity plan. Long-document RAG competes with short conversations. An agent may call the model to plan, interpret tool results, and compose its answer. Adding another application can therefore add far more inference traffic than its user count suggests. When additional GPUs are difficult to obtain, those interactions become the engineering problem.

**vLLM is also a scheduler: it decides how limited GPU resources are shared among inference requests.** Treating it only as an HTTP server misses the decisions that shape performance under load.

The objective is **maximum sustainable throughput per GPU within the service's latency and error SLOs**. Sustainable means a representative workload can keep running without an ever-growing queue or deteriorating reliability. A brief peak in tokens per second does not establish that capacity.

> Documentation checked: September 20, 2026, against the official `stable` documentation and its V1 guidance. These URLs move over time. Record the installed version, image digest, CLI help, startup logs, and `/metrics` schema for each experiment. All manifests, SLOs, workload quantities, and performance numbers below are **illustrative**, not measurements or disclosures from an employer.

## 2. What runs inside the Kubernetes Pod

The basic path is `Internal Application → Kubernetes Service → vLLM Pod → GPU`. A gateway can provide authentication and admission control in front of that path.

<VllmDiagrams kind="architecture" language="en" />

A Deployment maintains the Pods; a Service gives clients a stable destination when Pods change. GPU scheduling requires the appropriate driver and device plugin. If GPU requests and limits are both specified, they must match; specifying only the limit also establishes the request. CPU and RAM matter too: tokenization or frontend work can limit a GPU service. [Kubernetes GPU scheduling](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)

This **illustrative manifest is a starting point, not a deployment-ready configuration**. Replace the image placeholder with an approved pinned version, preferably also a digest. Provision verified model files in the PVC first. Size CPU, RAM, shared memory, and probe thresholds from measurements.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inference-example
spec:
  replicas: 1
  # Illustrative: avoids needing a spare GPU during replacement.
  # Recreate causes downtime; choose an availability plan separately.
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: inference-example
  template:
    metadata:
      labels:
        app: inference-example
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:REPLACE_WITH_PINNED_VERSION
          command: ["vllm", "serve"]
          args:
            - /models/approved-model
            - --host
            - "0.0.0.0"
            - --port
            - "8000"
            - --tensor-parallel-size
            - "1"
            - --max-model-len
            - "8192"
            - --gpu-memory-utilization
            - "0.90"
            - --max-num-seqs
            - "64"
            - --max-num-batched-tokens
            - "8192"
          ports:
            - name: http
              containerPort: 8000
          resources:
            requests:
              cpu: "4"
              memory: 16Gi
              nvidia.com/gpu: "1"
            limits:
              cpu: "8"
              memory: 32Gi
              nvidia.com/gpu: "1"
          volumeMounts:
            - name: model
              mountPath: /models
              readOnly: true
            - name: shm
              mountPath: /dev/shm
          startupProbe:
            httpGet: {path: /health, port: http}
            periodSeconds: 10
            failureThreshold: 60
          readinessProbe:
            httpGet: {path: /health, port: http}
            periodSeconds: 10
          livenessProbe:
            httpGet: {path: /health, port: http}
            periodSeconds: 30
            failureThreshold: 5
      volumes:
        - name: model
          persistentVolumeClaim:
            claimName: approved-model-pvc
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: 2Gi
---
apiVersion: v1
kind: Service
metadata:
  name: inference-example
spec:
  type: ClusterIP
  selector:
    app: inference-example
  ports:
    - port: 8000
      targetPort: http
```

A startup probe gives loading and warmup time before liveness checks can trigger restarts. Readiness controls traffic eligibility; liveness determines when a restart is necessary. Passing `/health` does not prove that latency meets an SLO. Tune timeouts and failure thresholds so overload does not become a restart loop. Memory-backed `/dev/shm` also consumes the container's memory budget. [Kubernetes probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/), [vLLM Kubernetes deployment](https://docs.vllm.ai/en/stable/deployment/k8s/)

Tensor parallelism spreads a model's computation across GPUs. Changing its degree requires checking the GPU allocation, model compatibility, and communication cost. It is different from increasing replicas: replicas are separate servers with their own weights and caches, while tensor-parallel workers cooperate on one model execution.

The manifest explicitly chooses `0.90` as an example. At the review date, the [serve CLI](https://docs.vllm.ai/en/stable/cli/serve/#--gpu-memory-utilization) documents **0.92** as the default. This is an executor **memory budget**, not a target for compute utilization. An explicit `--kv-cache-memory-bytes` overrides that automatic KV sizing. Pin a validated release and remeasure after upgrades.

## 3. Why expose a separate inference API?

With `Agents / RAG / Chat → API → vLLM → GPU`, applications can evolve independently of model deployment. Each application no longer needs to load its own weights or manage its own GPU process. HTTP also gives different client languages a common interface and provides a place to manage authentication, rate limits, usage, and observability.

The OpenAI-compatible API helps reuse existing clients, but compatibility is not a promise that every model supports every feature identically. Validate chat templates, parameters, tool calling, and streaming against the pinned runtime. [Official server documentation](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)

A shared service is also a shared bottleneck. Set input and output limits, bounded waiting, timeouts, cancellation propagation, and retry budgets. Otherwise, an agent retry loop can degrade unrelated applications. Check streaming through the entire path: a buffering proxy can delay visible output even when generation is fast.

An API key is not a complete security boundary. vLLM documents endpoints outside its API-key protection. Restrict exposed paths through a gateway or reverse proxy, enforce network isolation and NetworkPolicy, and provide TLS, user authorization, and quotas. Keep metrics on an internal monitoring path. A ClusterIP alone does not implement these controls. [vLLM Security](https://docs.vllm.ai/en/stable/usage/security/#api-key-authentication-limitations)

## 4. Prefill and decode have different costs

Prefill processes the prompt and prepares the state needed for generation. A long RAG context increases the amount of input work before the first answer token. Decode repeatedly generates the next token using the preceding tokens and stored state.

<VllmDiagrams kind="timeline" language="en" />

Prefill is often relatively compute-intensive; decode is often more sensitive to memory bandwidth. Hardware, model architecture, and batching can change the balance, so treat this as a diagnostic starting point. [vLLM tuning guide](https://docs.vllm.ai/en/stable/configuration/optimization/#chunked-prefill)

“Responses are slow” is not specific enough to choose a setting. Is the user waiting for output to begin, or does the stream slow down after it starts? A long input and a long output occupy the shared system in different ways.

## 5. KV cache is the memory cost of keeping requests active

Attention reuses keys and values for earlier tokens. The KV cache stores that state instead of repeatedly computing it. Active generation retains state across iterations, so fitting the weights in memory does not imply ample capacity for concurrent requests. [vLLM's APC introduction](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)

A useful intuition is:

```text
KV cache pressure ≈ active sequences
                  × sequence length
                  × model-dependent KV size
```

Sequence length includes the prompt and output generated so far. This is not an exact allocation formula: layers, KV heads, dtype, attention architecture, block allocation, prefix sharing, and parallelism all matter. Use runtime-reported KV capacity and measured peaks for sizing.

Long contexts, high concurrency, and long outputs compound each other. A request that fits when admitted can increase pressure as it generates. Also distinguish reserved GPU memory from occupancy within the KV pool. Framebuffer usage alone does not reveal how much additional concurrency the cache can sustain.

## 6. Continuous batching reuses capacity as requests finish

Requests rarely have identical input lengths or finish together. A static batch can leave capacity unused while its longest requests complete. Continuous batching rebuilds the runnable set at scheduling steps, removing completed requests and admitting eligible work.

Eligibility still depends on several constraints: available sequence slots, this iteration's token budget, KV capacity, and other scheduling restrictions. This is why “increase the batch size” is an incomplete recommendation. [Scheduler configuration](https://docs.vllm.ai/en/stable/api/vllm/config/scheduler/)

## 7. Sequence limits and token budgets are different controls

`max_num_seqs` caps **sequences processed per iteration**. `max_num_batched_tokens` caps **tokens processed per iteration**. Neither is the total queue length or requests per second. Their CLI forms are `--max-num-seqs` and `--max-num-batched-tokens`. [serve CLI](https://docs.vllm.ai/en/stable/cli/serve/)

<VllmDiagrams kind="budget" language="en" />

For an illustrative ordinary one-token decode step, 32 decoding sequences need roughly 32 tokens of iteration budget. Adding a 1,000-token prefill chunk would require roughly 1,032 tokens and 33 sequence slots. Yet those decoding requests may retain much more historical KV state. **Tokens computed in this step are not the same as tokens stored in memory.** Features such as speculative decoding change this simple accounting.

Increasing the sequence cap creates an opportunity for more concurrent work, but can increase KV demand and step duration. Increasing the token budget cannot bypass the sequence cap, and increasing the sequence cap cannot bypass the token or memory constraints.

Do not memorize a universal default for either control. The current [EngineArgs implementation](https://docs.vllm.ai/en/stable/api/vllm/engine/arg_utils/) resolves defaults using hardware, usage context, and configuration. Record the effective configuration, not just the command-line overrides.

## 8. Chunked prefill keeps long inputs from monopolizing a step

A large prefill can delay ongoing decode work. Chunked prefill spreads input computation over scheduling steps while preserving a single request's context. It does not mean splitting a document into separate application-level prompts.

V1 enables it by default where supported. Check the effective state of `--enable-chunked-prefill` and model support in startup logs; do not transfer V0 scheduling assumptions into V1. [Chunked prefill](https://docs.vllm.ai/en/stable/configuration/optimization/#chunked-prefill), [default resolution](https://docs.vllm.ai/en/stable/api/vllm/engine/arg_utils/)

## 9. Measure four groups together

Read latency, scheduling, GPU/KV state, and throughput on the same time axis. The table lists current documented V1 metric families. Counters normally expose `_total` samples; histograms expose `_bucket`, `_sum`, and `_count`. **Confirm exact names, labels, units, and HELP/TYPE in the running Pod's `/metrics`.** A missing metric is not a zero. [Production Metrics](https://docs.vllm.ai/en/stable/usage/metrics/)

| Group | Measurements | Documented metric families |
|---|---|---|
| User latency | TTFT / request TPOT / E2E; p50, p95, p99 | `vllm:time_to_first_token_seconds`, `vllm:request_time_per_output_token_seconds`, `vllm:e2e_request_latency_seconds` |
| Scheduler | Running / waiting / queue time / preemptions | `vllm:num_requests_running`, `vllm:num_requests_waiting`, `vllm:request_queue_time_seconds`, `vllm:num_preemptions` |
| GPU / KV | KV occupancy and GPU telemetry | `vllm:kv_cache_usage_perc` + DCGM |
| Throughput | Input/output tok/s; successful requests/s | Rates of `vllm:prompt_tokens`, `vllm:generation_tokens`, `vllm:request_success` |

Track `vllm:inter_token_latency_seconds` separately. KV occupancy is a ratio: **1 means 100%**. Older dashboards may reference `vllm:gpu_cache_usage_perc`; verify before reusing them. Check whether input counters include cached or newly computed tokens.

Useful NVIDIA exporter fields include `DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_FB_USED`, `DCGM_FI_DEV_FB_FREE`, and `DCGM_FI_DEV_MEM_COPY_UTIL`. Memory activity is different from memory capacity usage and is not directly a GB/s measurement. More detailed DRAM profiling depends on hardware support and collector configuration; do not assume it is enabled. [NVIDIA counter definitions](https://github.com/NVIDIA/dcgm-exporter/blob/main/etc/default-counters.csv)

These **illustrative PromQL queries** assume the series and labels have been verified. Add job, model, and deployment selectors appropriate to the monitored service.

```promql
histogram_quantile(
  0.95,
  sum by (le, model_name) (
    rate(vllm:time_to_first_token_seconds_bucket[5m])
  )
)

sum by (model_name) (rate(vllm:generation_tokens_total[5m]))

sum by (model_name) (increase(vllm:num_preemptions_total[5m]))
```

Aggregate histogram buckets before calculating a fleet percentile; do not average Pod p95s. Sparse observations or coarse buckets make p99 unreliable. Preserve per-replica views to detect imbalance. Client latency and gateway rejections, timeouts, and cancellations require additional instrumentation: successful server requests alone cannot describe the user experience.

## 10. TTFT and TPOT locate different symptoms

TTFT measures arrival to first token. A client measurement includes network and gateway delays that a server measurement may exclude. For streaming, define first content carefully so an empty role event does not count as an answer token.

```text
TTFT ≈ queue + prefill + scheduling/frontend overhead
TPOT = (last token time − first token time) / (output tokens − 1)
```

The TPOT formula applies to requests producing at least two tokens. Record how single-token outputs are handled. TPOT produces one average per request; ITL records individual intervals. Their percentiles therefore differ. Use TPOT to characterize overall generation speed and ITL to reveal pauses within streams. Align server and benchmark-client definitions before comparing values. [vLLM metrics design](https://docs.vllm.ai/en/stable/design/metrics/)

| Observation | Hypothesis to investigate | Next evidence |
|---|---|---|
| TTFT rises and queue grows | Arrival rate exceeds capacity, or admission/scheduling is constrained | Offered/completed RPS, queue trend, replica imbalance |
| TTFT rises with little queueing and long prompts | Prefill may dominate | TTFT by prompt length, prefill time, cache hits |
| TTFT is healthy but TPOT worsens | Decode concurrency, memory pressure, or step interference | ITL, active sequences, KV/DRAM activity, preemptions |

These are hypotheses, not diagnoses. If only client-visible TTFT worsens, inspect proxy buffering and the network before changing the scheduler.

## 11. Why look at p95 and p99, not just the average

An average can hide the minority of requests that wait much longer. p95 marks a boundary containing 95% of observations; p99 describes a rarer tail. Comparisons require consistent sample counts, time windows, and workload composition.

Agents chain model calls or wait for the slowest parallel branch. As an illustrative calculation, if ten independent calls each have a 95% chance of staying within a boundary, the chance that all ten do so is `0.95^10 ≈ 60%`. Real calls can be correlated through shared load, so this is an intuition, not a workflow forecast. Nor can you obtain workflow p95 by adding individual p95s. Measure workflow E2E directly.

## 12. Choosing an operating point with numbers

Every value below is **illustrative, not measured**. Imagine the same workload, GPU allocation, and observation window. GPU/KV utilization and waiting requests represent window averages; a real scorecard also needs peaks, distributions, and trends.

| Metric | Config A | Config B | Config C |
|---|---:|---:|---:|
| max_num_seqs | 32 | 64 | 128 |
| max_num_batched_tokens | 2,048 | 8,192 | 16,384 |
| GPU util | 56% | 87% | 96% |
| KV cache | 48% | 76% | 94% |
| waiting requests | 17 | 3 | 1 |
| TTFT p95 | 2.8s | 1.2s | 0.9s |
| TPOT p95 | 38ms | 44ms | 86ms |
| Output tok/s | 1,100 | 1,950 | 2,100 |
| Preemption | 0 | 0 | Observed |

For illustrative limits of TTFT p95 below 1.5s and TPOT p95 below 50ms, A misses the first-token target and C misses the generation target. C delivers about 7.7% more output throughput than B, but its TPOT p95 is about 95% longer. Its shorter queue does not compensate for the missed SLO, limited KV headroom, and preemptions that need investigation.

B is a **candidate based on those two latency targets**, not a proven winner. The table lacks E2E, error, OOM, and queue-trend evidence. If those also pass and repeated trials remain stable, B may be the better operating point. Distinguish an isolated preemption from sustained recomputation pressure.

Both parameters change across columns, so the table cannot establish which caused an improvement. Controlled experiments must change one at a time. Also, sustainable completions at a fixed offered load are ultimately arrival-limited. Different completion rates in a finite window are not automatically different capacity ceilings: inspect unfinished work, failures, output lengths, and arrival-rate sweeps.

## 13. Every parameter change spends something

With chunked prefill, a smaller token budget can favor decode ITL, while a larger budget can favor prefill progress and TTFT. These are tuning directions, not guarantees. [Official tuning guide](https://docs.vllm.ai/en/stable/configuration/optimization/#performance-tuning-with-chunked-prefill)

Ask whether a larger step addresses the current bottleneck. If first-token latency is already healthy but generation slows, define what would make a larger budget a successful experiment before trying it.

Apply the same reasoning to the sequence cap: is reduced queueing worth increased KV pressure, preemption, or tail latency? Recomputation can keep the GPU busy without increasing useful completions. Raising `gpu_memory_utilization` spends memory headroom; it is not a remedy that can ignore OOM risk or other GPU users.

There is no magic number. Long-context RAG and short chat replies need not share the same optimum. If one configuration cannot meet both SLOs, compare workload-specific admission controls or separate serving pools, including their resource cost.

## 14. Repeated prompts and prefix caching

Enterprise agents often repeat system instructions, shared prefixes, and RAG boilerplate. APC reuses matching prefix KV state to reduce input computation. It is neither semantic similarity search nor an answer cache, and it does not eliminate generation of new output. [Automatic Prefix Caching](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)

Default activation depends on model support. Verify `--enable-prefix-caching` and the effective configuration rather than assuming APC is active. [EngineArgs](https://docs.vllm.ai/en/stable/api/vllm/engine/arg_utils/)

Once the endpoint is verified, compare increases in `vllm:prefix_cache_hits_total` and `vllm:prefix_cache_queries_total` for a **token-based** hit ratio, alongside TTFT. Zero queries means the ratio is unavailable. Separate cold and warm cache tests and preserve realistic prefix repetition; repeatedly sending one identical prompt can exaggerate the benefit. [Metric definitions](https://docs.vllm.ai/en/stable/usage/metrics/)

Do not merge user-specific instructions or permissions to manufacture cache hits. Shared prefixes do not grant access to data, and tenant cache-isolation policies still apply.

## 15. A practical tuning loop

<VllmDiagrams kind="loop" language="en" />

**Step 1 — Describe the workload.** Separate chat, RAG, and agent traffic. Record prompt/output token p50/p95/p99, arrival RPS and bursts, concurrency, and mean and tail model calls per workflow. Equal daily request counts can hide very different peak demand.

**Step 2 — Set SLOs.** Illustrative starting targets are `TTFT p95 < 1.5s`, `TPOT p95 < 50ms`, and `E2E p95 < 8s`. Define the error budget and treatment of cancellations, timeouts, and rejections. Check whether the output-length distribution is compatible with the E2E target, and apply targets by workload.

**Step 3 — Measure the unchanged baseline.** Exclude warmup and hold dataset, output policy, arrival trace, and cache state constant across repeated runs. Open-loop RPS sweeps expose backlog because arrivals continue when responses slow. Closed-loop concurrency tests reduce arrivals as response times rise, potentially concealing overload. Use each deliberately and verify the load generator has capacity. [vLLM benchmark CLI](https://docs.vllm.ai/en/stable/cli/bench/serve/)

**Step 4 — Form a bottleneck hypothesis.** Low GPU utilization with a large queue warrants inspecting CPU throttling, tokenization, communication, gateway behavior, and replica imbalance as well as scheduler limits. High GPU/KV activity with preemption suggests a context/output/concurrency interaction. High GPU utilization with a small queue and healthy latency may already be a good result.

**Step 5 — Change one variable.** First vary the token budget at a fixed sequence cap; then compare sequence caps at the chosen budget. Explore interactions in a second pass. At each candidate and load level, report repetitions, sample counts, and variability, then establish the sustainable SLO-compliant limit.

The final scorecard should include offered/admitted/completed RPS, input/output tok/s, throughput per allocated GPU, SLO-compliant goodput, latency percentiles, errors, queue trend, KV peaks, and preemption rate. More raw tokens can mean less service value if more responses miss their targets. Define rollback triggers and preserve the previous image and configuration before testing.

## 17. GPU utilization is not the objective function

Tuning is a feedback loop: characterize workload, benchmark, inspect metrics, form a bottleneck hypothesis, change a parameter, and test again. The justification for a setting matters more than the setting itself.

High utilization and raw throughput are useful observations, but neither substitutes for response-time and reliability commitments. The operating point to choose is the one that sustainably completes the most useful work on the available GPUs while honoring those commitments.

**Loading the model onto a GPU is only the beginning. The real inference engineering starts after that.**
