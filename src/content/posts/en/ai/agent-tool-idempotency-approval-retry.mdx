<AnswerBlock question="Can an agent run a transfer tool exactly once?">
  In a distributed system, proving that a function ran exactly once is hard. You can still attach a durable action ID and idempotency key to one user intent, bind approval to a fingerprint of the exact arguments, and reuse the same key on external APIs and in PostgreSQL. Duplicate attempts converge on one business outcome; when the outcome is unknown, you do not open a second transfer—giving users an effectively-once experience.
</AnswerBlock>

The previous article, [**State Is Not an Event**](/en/ai/agents/state-is-not-event/), separated current snapshots from event history. Because events can be redelivered, the UI must handle the same event ID twice without changing outcome.

Agent tools are harder.

Rendering a progress event twice may look odd. Running a transfer tool twice moves money twice. Email sends, order creation, ad spend, and account deletion also create hard-to-reverse external effects.

Demo code often looks like this:

```python
if user_approved:
    return await transfer_money(
        recipient=action.recipient,
        amount=action.amount,
        currency=action.currency,
    )
```

In production you need answers to: what did the user approve? Did arguments change after approval? Double-clicks? Queue redelivery? Transfer succeeded but the worker died before reading the response? Which failures may retry?

This article uses a **transfer as a teaching example**. The code illustrates design ideas; it is not a real bank ledger, compliance program, or fraud stack.

## 1. Three meanings of “exactly once”

| Question | Meaning |
| --- | --- |
| Was the function invoked once? | In-process execution count |
| Was one HTTP request sent? | Network attempts |
| Did money move once? | Business side effect |

A worker timeout does not prove the provider did nothing—the transfer may have succeeded while the response was lost. Two HTTP calls with the same idempotency key can still yield one transfer if the provider dedupes.

Goal: **every retry for the same user intent converges on one business result**, not “one physical line of code.”

See also [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

## 2. Authentication, authorization, and approval

| Step | Question |
| --- | --- |
| Authentication | Who is this user? |
| Authorization | May they use the transfer tool? |
| Approval | May this recipient receive this amount **now**? |

Show tool name, recipient, amount, currency, fees, actor, and expiry. [OWASP’s transaction authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) applies the same idea to sensitive actions.

## 3. Do not execute the LLM proposal directly

Validate on the server, persist an action intent, then ask for approval. Approve by `action_id` only—never re-post tool JSON from the browser for execution.

```http
POST /tool-actions/action_123/approve
```

## 4. Fingerprint vs idempotency key

**Action fingerprint** — hash of tool name, schema version, canonical arguments, tenant, and actor; fixed at approval.

**Idempotency key** — identifies one user intent across retries, e.g. `tool-action:action_123`. Do not use `recipient + amount` as a global key; a second legitimate transfer would be blocked. Reject reuse of the same key with different arguments ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)).

## 5. PostgreSQL as source of truth

```sql
CREATE TABLE tool_actions (
    action_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    run_id UUID NOT NULL,
    tool_name TEXT NOT NULL,
    tool_version TEXT NOT NULL,
    arguments JSONB NOT NULL,
    action_fingerprint TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    status TEXT NOT NULL CHECK (
        status IN (
            'proposed', 'awaiting_approval', 'approved', 'executing',
            'succeeded', 'failed_retryable', 'failed_terminal',
            'outcome_unknown', 'cancelled', 'expired'
        )
    ),
    approved_fingerprint TEXT,
    approved_by UUID,
    approved_at TIMESTAMPTZ,
    approval_expires_at TIMESTAMPTZ,
    execution_attempt_id UUID,
    provider_reference TEXT,
    result JSONB,
    error JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (tenant_id, idempotency_key)
);
```

Use Redis for short locks and UI progress—not as the only dedupe for money movement.

## 6. Bind approval to stored actions

Re-read the stored row, check expiry, recompute fingerprint, and reject if arguments drifted after review.

## 7. One worker claims execution

Conditional `UPDATE ... WHERE status = 'approved' AND approved_fingerprint = action_fingerprint` so only one worker proceeds.

## 8. Same key at the provider

Pass the same `idempotency_key` on every retry. If the provider lacks idempotency or lookup APIs, the gap between “call succeeded” and “row saved” cannot be closed by app code alone.

## 9. Timeout may mean outcome unknown

<ToolExecutionSafetyDiagram kind="failure-window" language="en" />

Mark `outcome_unknown`, reconcile by key or provider reference—do not mint a new transfer.

## 10. Classify retries by certainty, not only error type

Schema and permission failures usually should not blind-retry. Connection failures before bytes are sent may retry with the same key. Response timeouts need `outcome_unknown` and lookup first. Provider 5xx behavior depends on the vendor contract.

## 11. Ack the queue after persisting results

Order: claim action → call provider → write terminal status in PostgreSQL → ack. If the worker dies after a successful write but before ack, redelivery must read `succeeded` and ack without calling the provider again.

## 12. Align checkpoints with tool side effects

Resuming from a checkpoint can re-enter a side-effecting tool node. Checkpoints continue graph execution; they do not dedupe external transfers. Tool handlers should load the durable action by ID ([LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)).

## 13. Compensation is not rollback

A completed transfer cannot be rolled back like a SQL transaction. A reversal is a new action with its own approval and idempotency key.

## 14. Test failure windows deliberately

Double approval clicks, duplicate queue delivery, argument changes after approval, worker death before and after provider success, timeouts with successful transfers, expired approvals, key reuse with different args, lost Redis locks, and checkpoint replays of tool nodes.

## 15. What matters more than “exactly once”

1. Bind approval to exact tool arguments.
2. One durable action ID per user intent.
3. Same idempotency key on every retry for that action.
4. When outcome is unknown, do not create a new side effect.
